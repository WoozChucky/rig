# defer: Code Run When Its Block Is Left Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Jai's `defer`: `defer Statement` and `defer Block`, registered when reached, run when the block it's written in is left by any way out (falling off its end, `return`, `break`, `continue`), a block's in reverse order, the innermost block's first; `defer` stops being a reserved word.

**Architecture:**
- **The parser** reads `defer S` into an `Ast_Defer` holding S, a block or any statement but a declaration, which it refuses. At the top level `defer` is refused. Each `defer` is a block level for the nesting limit, since its statement is a block of its own.
- **The checker** checks the deferred statement where the `defer` is, in a scope of its own, remembering it's inside deferred code (`Checker.deferring`, `defer_loops`): a `return` anywhere in it, or a `break`/`continue` whose loop is outside it, is refused. Reaching the end (6.11) is unchanged.
- **Lowering** keeps the defers reached so far in the blocks being lowered (`Lowering.defers`), each block remembering where its own start (a mark). Registering emits nothing. At each way out it lowers a copy of every deferred statement it leaves, last registered first, down to the mark of the block the jump lands in: at a block's end (if control gets there), at a `return` (all of them, after the return's values are worked out and the aggregates copied), at a `break` or `continue` (down to the loop body's mark). Each copy is at its own source positions, in an IR scope of its own inside the scope the `defer` was reached in. A body `#if` pushes no mark, so its defers are the enclosing block's. The interpreter runs the same IR, so `#run` needs nothing more than the walk of what it reaches.
- **Debug information** follows from the positions and scopes: stepping out of a block goes through the deferred lines in the order they run. `tests/debug/defer` proves it in gdb and cdb.

**Tech Stack:** C-style C++23 built with the pinned clang 23.1.5 (`build.bat`, `build.sh`), no STL; JavaScript (Node) for the VS Code extension's checks.

**Spec:** GitHub issue #149 (`gh issue view 149`), whose Decisions are settled design, restated below as binding; the decisions this plan makes; and `docs/rig-spec.md`, which Task 5 updates. Executors read all three.

## The maintainer's decisions (binding: the issue's, restated)

1. **Two forms**, `defer Statement` and `defer Block`. The statement is any statement but a declaration (`a deferred statement can't declare anything: its block ends when it runs`), `return`, `break` or `continue` (5). So `defer free(p);`, `defer count -= 1;`, `defer if open { close(); }`, `defer { a(); b(); }`. An expression that isn't a call is `only a call can be a statement, for now` (6.3).
2. **When it runs.** Registered when execution reaches it; runs when the block it is written in is left, by any way out: falling off its end, `return`, `break` or `continue` leaving it. A block's deferred statements run in reverse order of registration; leaving several blocks at once runs the innermost block's first, then each enclosing one's, up to the block the jump lands in. A `defer` not reached isn't registered.
   - A loop's body is a block, left at the end of every iteration: a `defer` in it runs once per iteration, before the next test or step, `continue` included.
   - A body `#if` makes no scope (#147): a `defer` in its taken branch belongs to the enclosing block.
3. **What it sees.** Evaluated when it runs, not when reached: `defer print_int(n);` prints `n` as it is when the block ends. It names what's in scope at the `defer`.
4. **Return values first:** `return e1, e2;` evaluates its values in order, copies each aggregate one into the caller's temporary (10.4), then the deferred statements run, then the procedure returns. In `x := 1; defer x = 2; return x;` the result is 1. Returning a view of memory a defer frees is a dangling view (8.6).
5. **What deferred code may not do:** leave itself other than by its end. A `return` anywhere inside it: `can't return from a deferred statement`; a `break` or `continue` whose loop is outside it: `'break' can't leave a deferred statement` (`'continue' ...`), at the keyword. A loop inside it may `break` and `continue`. A `defer` inside deferred code is allowed and runs when the deferred block ends.
6. **`main`:** its defers run before it returns to the C runtime, which then flushes the output streams (7.4).
7. **What doesn't run defers:** a runtime error (8.1); C's `exit`, compiled or called by a `#run`'s code (7.8).
8. **Top level:** `defer can only be in a body`, at the keyword. In a top-level `#run { ... }` `defer` works as in any body, `return;` included. A `defer` in code a `#run` runs behaves as compiled (10.8).
9. **Reaching the end** (6.11) is unchanged.
10. **Debug information** (10.7): the deferred code is lowered at each way out of its block, a copy per exit, each instruction at its own source position, so stepping out of a block goes from the `}` (or the `return`, `break`, `continue`) to the deferred lines, in the order they run, and then on. The issue's "a breakpoint on a deferred line has a location per copy" is corrected by the maintainer (Decision 12): what gdb and cdb do with such a breakpoint is accepted and documented. Runtime errors in deferred code name its own position. The jump out of a block stays at its `}`.
11. **Later:** `errdefer`; a defer that captures values when reached.

## Decisions this plan makes (where the issue leaves a choice)

"Decision N" alone, here and in the tasks, is one of these; the maintainer's are "the issue's Decision N".

1. **Task order:** parsing; checking and the refusals; lowering at each way out (with `#run`'s walk and the run tests); the debugger test; the spec and Basic's README. Each leaves both hosts green. Until Task 3, a program with a `defer` that gets past the parser and the checker isn't lowered by any test.
2. **Representation:** `AST_DEFER`, `Ast_Defer { Ast *statement; }`, pos at the `defer`. `defer { ... }` is the same node with an `Ast_Block` as its statement: the grammar is `defer = 'defer' statement`, a block being a statement. Dump: `(defer STATEMENT)`.
3. **A deferred statement is a block of its own**, for every stage: the checker checks it in a scope of its own; lowering lowers each copy as a block (its own mark, its own IR scope). So what a deferred `#if`'s taken branch declares ends with the deferred statement, and `defer defer f();` runs `f()` as soon as the outer deferred statement's copy ends (the issue's Decision 5: "a `defer` inside deferred code runs when the deferred block ends"). Only the statement right after `defer` is refused as a declaration; a declaration inside a deferred block, `if` or `#if` branch is that block's, and fine.
4. **The declaration refusal is the parser's**, at the declaration's first name (`Ast.pos` of the `Ast_Var`, `Ast_Const` or `Ast_Multi_Var`), after the declaration is read; the procedure is then given up, as after any syntax error (the parser has no recovery inside a body). A procedure or struct declaration in a body is refused before that, as today.
5. **`defer` at the top level** (and so inside a top-level `#if`'s branch) is refused by `parse_declaration` at the keyword; the declaration becomes a broken entry with no name and the parser skips to the next declaration, as for any failed one.
6. **Nesting limit:** each `defer` is one block level (MAX_DEPTH), counted in `p->blocks` and `reach_in_body` as `parse_block` counts a `{`; the one too many is `blocks are nested too deeply (more than 1000 levels)` at its `defer`. `defer { ... }` is two levels.
7. **Positions and leftovers of the checker's refusals:** `can't return from a deferred statement` at the `return`; its values are still checked as expressions (`check_expression`), so their own errors show, but against no result type. A `break` or `continue` in deferred code with no loop around it at all keeps `'break' is only allowed inside a loop`; the deferred message is for one whose innermost loop is outside the deferred statement. A refused jump keeps `loop` null.
8. **The checker's state:** `Checker.deferring` (the innermost `Ast_Defer` whose statement is being checked; null outside deferred code) and `Checker.defer_loops` (`c->loops.count` at it). `check_body` sets both aside and clears them, as it does the loops: a body a `#run` in deferred code reaches is checked as its own.
9. **Lowering's registration list:** `Lowering.defers` (`Array<Deferred>`, outermost block's first) and, per block that's left as a block, a mark (`l->defers.count` when it began): `lower_scoped_block`, `lower_loop_body` (the mark kept in `Loop.defers` for `break` and `continue`), `lower_body` (mark 0), and each copy of deferred code. A body `#if` takes no mark. A `return` runs every registered defer, a `break` or `continue` those from the innermost loop's mark, a block's end those from its own mark (only when control reaches the end: an IR block that has ended needs none). Each block then drops its registrations (`defers.count = mark`), ended or not. `lower_body` empties the list for each body (on demand, one Lowering lowers many), and drops the body's own at its end, as every block does; it can't use `leave_block` there, since a body with results lowers no copy before its `unreachable` (Decision 11).
10. **Each copy** is lowered in a new `Ir_Scope` at the deferred statement's position (`statement_position`), whose parent is the scope current where the `defer` was reached (`Deferred.scope`); a deferred block's statements go straight into that scope (`lower_block`, not `lower_scoped_block`). So each copy's locals are variables of their own, in a scope of their own, and a debugger shows them inside it.
11. **Positions around the copies** (settled by the maintainer): a copy's instructions are at their own statements' positions. A copy per exit, with no guard or shared copy: the code size is accepted. After the copies, the instruction that leaves stays where it is today, so stepping goes keyword, deferred lines in order, keyword again, out: a `return`'s `ret` and a `break`'s or `continue`'s `jump` at its keyword (so a debugger shows that line again before leaving, as it shows a loop's keyword again after each iteration), the jump out of an `if`'s block at its `}`, a loop body's jump to its test or step at the loop's keyword, the body's `ret` at its `}`. A block statement has no jump at its `}`, so after its copies the debugger goes on to the next statement. A `defer` statement itself emits nothing: its line has code only where its copies are. No copy is lowered before the `unreachable` that ends a body with results whose end can't be reached.
12. **What the debuggers do with copies** (Fact 8): cdb refuses a line breakpoint on code in several pieces (`Ambiguous symbol error`), as it does on a `for` line; gdb keeps one location per line per lexical block, and LLVM writes a lexical block only for a scope that holds a variable, so the copies of a deferred statement that declares no local are one location, at the first copy in the code. Settled by the maintainer: accepted and documented, with no artificial variables to force a lexical block per copy. Task 4 documents it (`CONTRIBUTING.md`) and Task 5 in 10.7 (and 6.12), plainly, correcting the issue's "a location per copy"; the debugger test pins stepping, which works in both.
13. **Test names:** `tests/run/defer`, `defer_main`, `defer_run` (with `.build.out`), `defer_exit`, `defer_runtime_error`; `tests/errors/defer_refused`; `tests/debug/defer`.

## Review Focus

1. **A loop inside deferred code, and deferred code at a loop's `break` or `continue`:** a jump must run only the defers registered since its own loop's body began, never an outer block's, and a jump inside deferred code only the deferred code's own. Task 3's `defer_runs_when_break_and_continue_leave_nested_blocks` and `tests/run/defer`'s `looping` and `nested_break`.
2. **Deferred code that declares locals, copied at several exits:** each copy has its own slot, scope and variable; no slot or variable shared between copies, none declared twice in one scope. Task 3's `deferred_code_is_at_its_own_lines`.
3. **`#run` and deferred code both ways:** a `#run` reaching a procedure with defers runs them as compiled (and gives the value worked out before them); a `#run` inside deferred code checks the body it reaches as its own, its `return`s and `break`s not refused. Task 2's `a_run_in_deferred_code_checks_its_body_as_its_own`, Task 3's `defer_in_code_a_run_runs` and `tests/run/defer_run`.
4. **The loop list growing while a jump's copies are lowered:** deferred code holding loops pushes onto `l->loops`, which may move it; a `Loop *` taken before the copies is stale after. Task 3's `deferred_loops_at_a_break_build` (20 nested loops in the deferred code at a `break`, through `builds`).
5. **Many exits:** an `else if` chain of 10000 arms, each returning after a `defer`, is 10000 copies, lowered in a loop, nothing recursive per arm. Task 3's `defer_before_an_else_if_chain_of_10000_returns`.
