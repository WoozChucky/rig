# libm on Linux and Basic's Math Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** On Linux every program links glibc's `libm` beside `libc`, and the interpreter finds `libm`'s functions after `libc`'s, so `#foreign libc` reaches C's `<math.h>` on both systems, compiled and interpreted; and Basic's `math.rig` gains `PI`, `TAU` and 21 math procedures for each of `float64` and `float32`, over C's functions.

**Architecture:**
- **The link line** (`src/link.cpp`'s `link_command_linux`) gains `-lm` right after `-lc`. Windows' doesn't change.
- **The interpreter's lookup** (`src/os_linux.cpp`'s `os_find_c_function`) takes a second handle, `libm.so.6` with `RTLD_NOLOAD` (the compiler links `-lm` itself), and searches it when `libc.so.6` hasn't the name. Still never `RTLD_DEFAULT`. Windows' lookup doesn't change.
- **`hypotf` on Windows** (the maintainer's change, below): the UCRT exports `hypotf` only as `_hypotf` (Fact 3), so `src/ir.cpp`'s `WINDOWS_C_NAMES` maps the C name `hypotf` to `_hypotf`, as it maps the time functions to their 64-bit names (#161): the backend declares it so, and the interpreter looks it up the same way (its own table's `hypotf` first, as for C17's time functions). `frexpf`, `ldexpf` and `fabsf` have no export at all and aren't mapped: spec 10.6 says they aren't available compiled on Windows.
- **Basic:** `libc.rig` declares C's double and float functions under `c_` names (`c_sqrt`, `c_sqrtf`); `math.rig` wraps each in a procedure named by type (`sqrt_float64`, `sqrt_float32`) that only calls it, `hypot_float32` included (`c_hypotf`, linked to `_hypotf` on Windows).
- **Tests:** `tests/unit/test_link.cpp`, `tests/unit/test_interp.cpp` and `tests/unit/test_llvm.cpp` for the compiler, a new `tests/run/foreign_math.rig` declaring C's functions itself (`hypotf` among them), and `tests/run/basic_math.rig` extended with a line per new procedure.

**Tech Stack:** C-style C++23 built with the pinned clang 23.1.5 (`build.bat`, `build.sh`), no STL; Rig as `docs/rig-spec.md` describes it (milestone 4 so far: `#import`, `#run`, `#if`).

**Spec:** GitHub issue #148 (`gh issue view 148`), whose Decisions are settled design, restated below as binding; the maintainer's settlements and the decisions this plan makes; and `docs/rig-spec.md`, which Tasks 1, 2 and 3 update (7.6, 10.6, 10.8). Executors read all three. Basic v1's plan, `docs/superpowers/plans/2026-11-17-basic-v1.md`, is the precedent for Basic's style. Related: #125 (Rig's own runtime; see Decision 2).

## Decisions (issue #148's, binding)

1. **Linking (Linux):** the link line gains `-lm` after `-lc`: `... OBJECTS... -LCRT -lc -lm CRT/crtn.o`. Every program then depends on `libm.so.6`, used or not (no `--as-needed`): it is in glibc's own package (`libc6`), on every machine that has `libc.so.6`, so nothing new needs installing. Windows' link line doesn't change.
2. **#125:** when Rig links with its own runtime, it links `libm.so.6` directly, beside `libc.so.6`. Whichever lands second carries the other's change. #125 hasn't landed (Fact 9), so this plan links `-lm`. If `git log origin/main` shows #125 merged before Task 1 starts, stop and report: the facts above would be stale.
3. **The interpreter (Linux):** `os_find_c_function` searches `libc.so.6` first, as now, then `libm.so.6`, a handle taken with `RTLD_NOLOAD` as for libc. Still not `RTLD_DEFAULT`, which would find libstdc++'s functions a program can't call. Windows' lookup doesn't change.
4. **The library's name stays `libc`** (7.6's message unchanged). `libc` names the platform's C runtime: on Linux glibc's `libc` and `libm`, as it is the UCRT and `kernel32` on Windows.
5. **Basic's `math.rig` gains**, named by type (no overloading; C's names stay free for programs, C's functions declared in `libc.rig` under `c_` names):
   - `PI :: 3.141592653589793;` and `TAU :: 6.283185307179586;`, untyped float constants;
   - for `T` in `float64` and `float32`: `sqrt_T`, `cbrt_T`, `sin_T`, `cos_T`, `tan_T`, `asin_T`, `acos_T`, `atan_T`, `atan2_T(y, x)`, `exp_T`, `exp2_T`, `log_T`, `log2_T`, `log10_T`, `pow_T(base, exponent)`, `hypot_T(x, y)`, `floor_T`, `ceil_T`, `round_T` (half away from zero, C's `round`), `trunc_T`, and `mod_T(a, b)` (C's `fmod`: the remainder with `a`'s sign);
   - each calls C's function of the same type (`sqrt` for `float64`, `sqrtf` for `float32`). Where a `float32` one doesn't link and run on both systems both ways, Basic's `float32` version calls the `float64` one and converts back, and the README says so. (`hypotf` was the only one, Fact 3; the maintainer's settlement 1 maps it to `_hypotf` on Windows instead, so no procedure falls back.)
6. **Results** are the C library's. A domain error gives NaN, and C's `errno` isn't exposed. Tests print with few enough decimals that the systems and both ways agree, and the README says that the last bit can differ between the compiled and the interpreted program on Windows.

## Decisions this plan makes

1. **No `float32` fallback** (settled above): all 21 `float32` procedures call C's `...f` function, `hypot_float32` included (`c_hypotf`, linked to `_hypotf` on Windows by Task 3).
2. **The C layer's names** are `c_` and C's name: `c_sqrt`, `c_sqrtf`, ..., `c_fmod`, `c_fmodf` (`mod`'s C function is `fmod`). Their parameters are C's: `x` for one, `c_atan2(y, x)`, `c_pow(x, y)`, `c_hypot(x, y)`, `c_fmod(x, y)`.
