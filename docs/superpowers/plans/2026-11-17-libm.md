# libm on Linux and Basic's Math Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** On Linux every program links glibc's `libm` beside `libc`, and the interpreter finds `libm`'s functions after `libc`'s, so `#foreign libc` reaches C's `<math.h>` on both systems, compiled and interpreted; and Basic's `math.rig` gains `PI`, `TAU` and 21 math procedures for each of `float64` and `float32`, over C's functions.

**Architecture:**
- **The link line** (`src/link.cpp`'s `link_command_linux`) gains `-lm` right before `-lc`. Windows' doesn't change.
- **The interpreter's lookup** (`src/os_linux.cpp`'s `os_find_c_function`) takes a second handle, `libm.so.6` with `RTLD_NOLOAD` (the compiler links `-lm` itself), and searches it when `libc.so.6` hasn't the name. Still never `RTLD_DEFAULT`. Windows' lookup doesn't change.
- **Basic:** `libc.rig` declares C's double and float functions under `c_` names (`c_sqrt`, `c_sqrtf`); `math.rig` wraps each in a procedure named by type (`sqrt_float64`, `sqrt_float32`) that only calls it. `hypotf` doesn't link on Windows (Fact 2), so `hypot_float32` calls `c_hypot` and rounds.
- **Tests:** `tests/unit/test_link.cpp` and `tests/unit/test_interp.cpp` for the compiler, a new `tests/run/foreign_math.rig` declaring C's functions itself, and `tests/run/basic_math.rig` extended with a line per new procedure.

**Tech Stack:** C-style C++23 built with the pinned clang 23.1.5 (`build.bat`, `build.sh`), no STL; Rig as `docs/rig-spec.md` describes it (milestone 4 so far: `#import`, `#run`, `#if`).

**Spec:** GitHub issue #148 (`gh issue view 148`), whose Decisions are settled design, restated below as binding; the decisions this plan makes; and `docs/rig-spec.md`, which Tasks 1 and 2 update (7.6, 10.6, 10.8). Executors read all three. Basic v1's plan, `docs/superpowers/plans/2026-11-17-basic-v1.md`, is the precedent for Basic's style. Related: #125 (Rig's own runtime; see Decision 2).

## Decisions (issue #148's, binding)

1. **Linking (Linux):** the link line gains `-lm` before `-lc`: `... OBJECTS... -LCRT -lm -lc CRT/crtn.o`. Every program then depends on `libm.so.6`, used or not (no `--as-needed`): it is in glibc's own package (`libc6`), on every machine that has `libc.so.6`, so nothing new needs installing. Windows' link line doesn't change.
2. **#125:** when Rig links with its own runtime, it links `libm.so.6` directly, beside `libc.so.6`. Whichever lands second carries the other's change. #125 hasn't landed (Fact 9), so this plan links `-lm`. If `git log origin/main` shows #125 merged before Task 1 starts, stop and report: the facts above would be stale.
3. **The interpreter (Linux):** `os_find_c_function` searches `libc.so.6` first, as now, then `libm.so.6`, a handle taken with `RTLD_NOLOAD` as for libc. Still not `RTLD_DEFAULT`, which would find libstdc++'s functions a program can't call. Windows' lookup doesn't change.
4. **The library's name stays `libc`** (7.6's message unchanged). `libc` names the platform's C runtime: on Linux glibc's `libc` and `libm`, as it is the UCRT and `kernel32` on Windows.
5. **Basic's `math.rig` gains**, named by type (no overloading; C's names stay free for programs, C's functions declared in `libc.rig` under `c_` names):
   - `PI :: 3.141592653589793;` and `TAU :: 6.283185307179586;`, untyped float constants;
   - for `T` in `float64` and `float32`: `sqrt_T`, `cbrt_T`, `sin_T`, `cos_T`, `tan_T`, `asin_T`, `acos_T`, `atan_T`, `atan2_T(y, x)`, `exp_T`, `exp2_T`, `log_T`, `log2_T`, `log10_T`, `pow_T(base, exponent)`, `hypot_T(x, y)`, `floor_T`, `ceil_T`, `round_T` (half away from zero, C's `round`), `trunc_T`, and `mod_T(a, b)` (C's `fmod`: the remainder with `a`'s sign);
   - each calls C's function of the same type (`sqrt` for `float64`, `sqrtf` for `float32`). Where a `float32` one doesn't link and run on both systems both ways, Basic's `float32` version calls the `float64` one and converts back, and the README says so.
6. **Results** are the C library's. A domain error gives NaN, and C's `errno` isn't exposed. Tests print with few enough decimals that the systems and both ways agree, and the README says that the last bit can differ between the compiled and the interpreted program on Windows.
7. **Tests:** unit tests for the Linux link command and the interpreter finding `sqrt`; a `tests/run` program declaring C's math functions itself; `basic_math` extended to every new procedure with the edge cases (zero, `-0.0`, infinities as `1 / zero`, NaN, `atan2` in each quadrant, `round` at halves, `mod` with negative operands), printed with `print_float` at 6 decimals or fewer. No new `tests/errors`.
8. **Docs:** Basic's README lists the new procedures and constants; the spec's 7.6, 10.6 and 10.8 change in this PR.

## Decisions this plan makes

1. **`hypot_float32` is the one fallback** (Fact 3): `hypotf` doesn't link compiled on Windows, and the other 20 float functions link and run on both systems both ways. So `libc.rig` declares no `c_hypotf`, and `hypot_float32` is `cast(float32) c_hypot(x, y)`: the `float32` arguments widen exactly, `hypot` of them in `float64` can't overflow, and the cast rounds once (an infinity past `float32`'s range, Fact 6).
2. **The C layer's names** are `c_` and C's name: `c_sqrt`, `c_sqrtf`, ..., `c_fmod`, `c_fmodf` (`mod`'s C function is `fmod`). Their parameters are C's: `x` for one, `c_atan2(y, x)`, `c_pow(x, y)`, `c_hypot(x, y)`, `c_fmod(x, y)`. Basic's procedures take `x` for one, and the issue's names for two: `atan2_T(y, x)`, `pow_T(base, exponent)`, `hypot_T(x, y)`, `mod_T(a, b)`.
3. **Layout:** `libc.rig` gains, at its end, a section for C's `<math.h>`: the 21 double declarations (Task 3), then the 20 float ones (Task 4), each block in the issue's order. `math.rig` gains `#load "libc.rig";`, and after `abs_float64`, `PI` and `TAU`, then the 21 `float64` procedures (Task 3), then the 21 `float32` ones (Task 4), in the issue's order. The README's Math section gives each function one line naming both types, as `min`'s line does (`` `sqrt_float64`, `sqrt_float32` `(x: T) -> T`: ... ``): Task 3 writes it with the `float64` name, Task 4 adds the `float32` one.
4. **Each procedure is the call and nothing else** (`return c_sqrt(x);`), so `-0.0`, infinities and NaN reach C and come back as C gives them.
5. **The tests print `float64` results with 6 decimals and `float32` ones with 4** (Fact 5).
6. **The libm handle** is a second `static` beside libc's, taken once; a null handle (for either) is skipped rather than ending the lookup.
7. **The run test of C's own names** is `tests/run/foreign_math.rig`, printing with `printf` (no Basic, and no NaN, which the two C libraries' `printf`s print differently).
8. **`site/install.md`'s Linux requirement** names `libm.so` beside `libc.so`.

## Review Focus

1. **A name both `libc.so.6` and `libm.so.6` export** (`copysign`, `frexp`, `ldexp`, `modf`, `scalbn`, Fact 1) must still come from libc at compile time, as before: libm is searched only after libc. Task 2's unit test pins `copysign`.
2. **The compiler's other libraries stay out of reach:** a libstdc++ (or LLVM) symbol must not resolve interpreted, since no compiled program could link it. Task 2's unit test pins `_ZSt9terminatev`.
3. **`-0.0`, infinities and NaN through Basic's wrappers:** a wrapper that does anything but the call (an `if`, an `abs`, an `x + 0`) loses `-0.0`'s sign or a NaN. Tasks 3 and 4 print `-0.0` results for every procedure that has one, and the infinities and NaN.
4. **Each `float32` procedure computes in `float32`**, calling C's `...f` function, but `hypot_float32`: the tests at 4 decimals can't tell `sinf(x)` from `cast(float32) sin(x)`, so the reviewer reads each one. `hypot_float32` of two `float32`s whose hypotenuse is past `float32`'s range gives `inf` (Task 4).
5. **`PI` and `TAU` stay untyped:** `p32 : float32 = PI;` must compile (a `float64` constant wouldn't convert), and `show32(PI)` takes it as a `float32` (Task 3). The README says that `x := PI;` makes a `float32`, an untyped float's default.
