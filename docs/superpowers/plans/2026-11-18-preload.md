# Preload: the Module Every Program Imports Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Jai's Preload: `modules/Preload`, a module of Rig source that every program imports without asking, holding what the language itself refers to, with Basic's `Allocator`, its modes and the heap allocator moved into it.

**Architecture:**
- **The loader** (`load_program`) reads Preload's `module.rig` right after the main file (file 1 in reading order) and places it **first in load order, before the main file** (`walk_in_load_order`, #147's load order), so Preload's declarations come first and win a clash: found in the places as any module is (`module_lookup`), known by its identity as any file is, so an explicit `#import "Preload";` or a `#load` of its path reads nothing more. The main file stays first in reading order: file index 0, the name rig reports, `--stdin-for`, the program's own diagnostics. Every entry point loads through `load_program`, so `rig build`, build programs and their workspaces, `rig check` (with `--stdin` and `--stdin-for`) and `bin/unit-tests --interpret` all get it, and the compile-time world with them.
- **A Preload that can't be found or read** stops the loading before anything is parsed: the loader records why in `Ast_File.load_failure`, and the driver says it as `rig: error: MESSAGE`, status 1 (interpret mode as `unit-tests: error: MESSAGE`).
- **The move:** the four modes, `Allocator`, `heap_allocator_proc` and `HEAP_ALLOCATOR` leave `modules/Basic/allocators.rig` for `modules/Preload/module.rig`, the heap over Preload's own `__malloc`, `__realloc` and `__free`. Basic keeps its helpers, the arena and the pool, and its `c_` C declarations.

**Tech Stack:** C-style C++23 built with the pinned clang 23.1.5 (`build.bat`, `build.sh`), no STL; Rig for the modules; JavaScript (Node) for the VS Code extension's checks.

**Spec:** GitHub issue #151 (`gh issue view 151`), whose Decisions are settled design, restated below as binding; the decisions this plan makes; and `docs/rig-spec.md`, which Task 5 updates. Executors read all three. Later issues fill Preload in and are not part of this plan: #152 (command-line arguments), #153 (type info and `Any`), #156 (the context).

## The maintainer's decisions (binding: the issue's, restated)

1. **Where.** `modules/Preload/module.rig`, beside `Basic` and `Compiler`, found in the two places modules are (2.14), with a `README.md` listing what it declares, as Basic's does. Its files are a module's files, so they may declare `#compiler` procedures.
2. **Every program imports it**: ordinary programs, build programs and their workspaces, `rig check` (with `--stdin` and `--stdin-for`) and `bin/unit-tests --interpret`. Writing `#import "Preload";` is allowed and reads nothing more.
   - **Load order (settled by the maintainer, changing the issue's "right after the main file"):** Preload comes **first** in load order (2.13), before the main file, so Preload's declarations always win a clash: a program declaring `Allocator` gets the issue's own message, `'Allocator' is already declared at @MODULES@/Preload/...`, at the program's declaration, and Preload's `HEAP_ALLOCATOR` keeps working; a program's own `__runtime_init` or `__save_command_line` (later issues) can't replace Preload's. With a workspace: Preload first, then the workspace's files. Only load order (#147's: the declarations' order, the "already declared" rule, the top-level `#run`s' order, top-level checking) puts Preload first, through #147's machinery (`walk_in_load_order`, `Source_File.order`, `Ast_File.order`), not a second mechanism. The main file stays the first file in reading order: file index 0, the name rig reports, `--stdin-for`, the program's own diagnostics.
   - When it can't be found: `rig: error: there's no module 'Preload' (looked in DIR1 and DIR2)`, status 1, before anything is checked.
   - Its files are named by their absolute paths, so tests' expectations write them `@MODULES@/Preload/...`.
3. **One top level:** Preload's declarations join the program's, so a program can't declare a name Preload declares. Every name Preload declares for its own use starts with two underscores (`__malloc`), and only the names its README lists are for programs. The underscores are a convention, not enforced.
4. **What moves from Basic** (`allocators.rig`), unchanged in name and meaning: `ALLOCATE`, `RESIZE`, `FREE`, `FREE_ALL`; `Allocator`; `heap_allocator_proc` and `HEAP_ALLOCATOR`, over Preload's own `__malloc`, `__realloc` and `__free` (`#foreign libc "malloc"` and so on). Basic's `c_malloc`, `c_realloc` and `c_free` stay in `libc.rig`. Basic keeps `alloc`, `resize`, `free`, `free_all`, the arena and the pool, and its README points at Preload's for what moved. Programs that import Basic see no difference.
5. **Later, by issue** (Preload's README grows with them): command-line arguments (#152), type info and `Any` (#153), the context (#156).
6. **Cost:** Preload's procedures are part of every program and lowered as any procedure is; nothing runs that the program doesn't call; nothing new is linked.
7. **The compile-time world** (7.8) has Preload too, its globals (none yet) in the interpreter's memory.
8. **Done when:** the module, the implicit import everywhere, the move; the archives carry `modules/Preload` (only the packaging scripts' comments change); the tests below; spec 2.13, 2.14, 4.6, 9.3, 10.2 and 10.6 updated in the same PR.

## Decisions this plan makes (where the issue leaves a choice, or the code decides)

1. **Task order:** the module and the implicit import in the loader (Preload empty); the missing-Preload error in the driver, interpret mode and the runner; the move; packaging and docs; the spec. Each leaves both hosts green. Preload stays empty until Task 3, since its names would clash with Basic's until they move together.
2. **Reading order and load order:** Preload is read right after the main file, before a workspace's further files (reading order: main file, Preload, the further files in their order, then the main file's own loads), so Preload is file 1 of every program. Load order: Preload, the main file, the further files in their order, then the main file's own loads. A further file that is Preload's `module.rig` adds nothing.
3. **How the failure travels:** the loader sets `Ast_File.load_failure` (the message, without `rig: error: `) and returns at once, with only the main file registered and nothing parsed, so no diagnostic is ever made; `compilation_load` prints it before the `--stdin-for` answers and returns false. The loader prints nothing itself, as now.
4. **A Preload `module.rig` that is there but can't be read** (a directory, say) is `rig: error: cannot read 'PATH': MESSAGE`, the main file's words, PATH its absolute path: no `#import` names it, so there's no string to report it at either.
5. **Interpret mode** says the same message as `unit-tests: error: MESSAGE`, status 1, as it says its own `cannot read`: bin/unit-tests is not rig.
6. **Where Preload is looked for:** in the places the loading uses, `Load_Options.modules` when given, as any module. `Load_Options.no_preload` (new; rig never sets it) leaves Preload out, for the unit tests of the loader's other rules, which assert file counts and indexes and use places of their own with no Preload: every existing `load_program` call in `test_load.cpp` sets it, and so do `lower_records_every_source`, `debug_info_names_each_procedures_file` and `run_build_program` when given its own places. The other tests that load keep Preload.
7. **The file given with its text** (`--stdin-for`) may be Preload's `module.rig`: its text is taken where Preload is read, and the program reaches it. A main file that is Preload's `module.rig` reads nothing more.
8. **One file:** Preload is `module.rig` alone for now; the allocator comes first in it, so that the later issues' additions go below and the line `tests/errors/preload_name_taken.err` names stays put.
9. **A program's own declaration of a Preload name** is reported at the program's declaration, naming Preload's (Fact 2; Preload first in load order), as the issue's Done-when has it: `tests/errors/preload_name_taken.rig:6:1: error: 'Allocator' is already declared at @MODULES@/Preload/module.rig:A:1`, and nothing else: every use of the name, the program's and Preload's, finds Preload's `Allocator`, so `HEAP_ALLOCATOR` keeps working. The test pins both.
10. **Basic after the move:** `allocators.rig` loads `memory.rig` alone (it calls nothing of `libc.rig` any more). `c_malloc`, `c_realloc` and `c_free` stay, as the issue says, though Basic no longer calls them; `libc.rig`'s and the README's "the only C functions Basic calls" become "the C functions Basic declares", and the three are described as C's heap for programs and for Basic, Preload's heap allocator declaring its own.
11. **The spec** also gets 2.1, 7.8, 7.9 and 10.1 (each a sentence or a clause), besides the issue's six sections, and an example in 2.14, the issue's program.
12. **Test names:** loader tests in `test_load.cpp` under `// Issue #151: Preload (spec 2.13, 2.14).`; `tests/run/preload_heap_allocator`, `tests/run/preload_imported_too`, `tests/errors/preload_name_taken`; runner cases `no_preload_test` and `check_stdin_for_preload_test`.
