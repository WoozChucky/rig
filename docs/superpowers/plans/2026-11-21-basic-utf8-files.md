# Basic's UTF-8 Files on Windows, and Basic v2's Polish: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** On Windows, Basic's files, the environment's variables and commands take and give UTF-8, compiled, interpreted and in a `#run`, as its directories already do (#209); and the wording and tidying left by Basic v2's reviews is done (#211).

**Architecture:**
- **Basic over `kernel32`'s wide calls** (Q1 (a), Q2 (a)). A new `modules/Basic/wide.rig` holds the UTF-8 to UTF-16 conversions, `to_wide_path` moving there from `directory.rig`. On Windows, `file.rig` opens, reads, writes, sizes, closes and deletes through `CreateFileW`, `ReadFile`, `WriteFile`, `GetFileSizeEx`, `CloseHandle` and `DeleteFileW`; `get_environment` reads `GetEnvironmentVariableW`; `run_command` and `run_command_with_output` start the shell with `CreateProcessW`, the output through `CreatePipe`. Each procedure chooses with a statement `#if`, as the directories do. Linux keeps C's stdio, `getenv`, `system` and `popen`, unchanged.
- **No compiler, link or build change for #209**, and no spec change but one list: `kernel32`'s functions resolve compiled and interpreted today (Facts 6-8). Spec 7.10's list of Basic's short-lived heap memory (`2642`) gains the Windows heap scratch Tasks 2 and 3 add. #211's last task changes comments, one diagnostic and docs.
- #211's interpreter edge (a Rig procedure reaching C through memory) is not in this plan: it is #212 (Q3).

**Tech Stack:** C-style C++23, built with the pinned clang 23.1.5 (`build.bat`, `build.sh`), no STL. Rig for Basic and Preload.

**Spec:** issues #209 and #211 (`gh issue view 209`, `gh issue view 211`); `docs/rig-spec.md`, which Task 4 changes, and Tasks 2 and 3 only in 7.10's heap list (`2642`); `modules/Basic/README.md`. The code on `main` at 59b1383 is what the Facts describe, and it wins where an issue's line numbers are older. Executors read all three.

## Decisions this plan makes

"Q1" to "Q3" are the maintainer's settled answers (the last section); each is the recommended option.

1. **Four tasks, one PR**, each green on both hosts: 1. `wide.rig` and files; 2. the environment; 3. commands, and the docs that sum #209 up; 4. #211's polish.
2. **`wide.rig`** (Task 1), its whole body in `#if OS == OS_WINDOWS`, loading `libc.rig`, `string.rig`, `allocators.rig`; `file.rig`, `directory.rig` and `environment.rig` load it; `module.rig` loads it after `path.rig`:
   - `to_wide_string :: (s: string, allocator: Allocator, loc: Source_Code_Location = #caller_location) -> *u16`: `s` in UTF-16 with a zero unit after it, one allocation from `allocator` at `loc`, which the caller frees with `free(wide, allocator, loc)`. Null, with nothing allocated, for a zero byte, bytes that aren't valid UTF-8 (`C_MB_ERR_INVALID_CHARS`), more than 2147483647 bytes, or no memory. The empty string is a lone zero unit (`MultiByteToWideChar` refuses a count of 0, Fact 8 of #157's plan, so it isn't asked).
   - `to_wide_path :: (path: string) -> *u16`: today's contract, moved: null for an empty path, else `to_wide_string(path, HEAP_ALLOCATOR)`.
   - `from_wide_string :: (wide: *u16, units: int, allocator: Allocator, loc: Source_Code_Location = #caller_location) -> string, bool`: `units` UTF-16 units (no zero) as UTF-8 in one allocation of the exact size, an unpaired surrogate becoming U+FFFD; 0 units is the zeroed string and true, allocating nothing; no memory or a failed conversion is the zeroed string and false.
3. **Files on Windows** (Task 1). `File.handle` is `kernel32`'s file handle there and C's `FILE *` on Linux, null when not open (`INVALID_HANDLE_VALUE` is never kept). The path's wide copy is `to_wide_path`'s, from the heap, freed as soon as `CreateFileW` returns (today's reasons, `file.rig:17-24`), so no allocation count changes. `file_open`: `FILE_READ` is `GENERIC_READ`, `OPEN_EXISTING`; `FILE_WRITE` `GENERIC_WRITE`, `CREATE_ALWAYS`; `FILE_APPEND` `FILE_APPEND_DATA`, `OPEN_ALWAYS` (writes land at the end); share 3 in all; `FILE_ATTRIBUTE_NORMAL`; no template. A directory fails to open in every mode (Fact 6), so Windows needs no probe read and no `defer`. `file_read`: one `ReadFile` of at most 2^30 bytes, its count, or 0 when it fails. `file_write`: `WriteFile` in pieces of at most 2^30 bytes, each going on where the last stopped, false when one fails or writes 0. `file_size`: `GetFileSizeEx`, -1 when it fails. `file_close`: `CloseHandle`. `write_entire_file` and `append_to_file`: `closed` is `c_close_handle(...) != 0` on Windows. `delete_file`: `file_exists` first, as now, then `DeleteFileW(wide) != 0`. A path that isn't valid UTF-8 is refused on Windows, false, as the directories refuse it; Linux passes its bytes as now.
4. **The environment on Windows** (Task 2). `get_environment` keeps its refusals and its two allocations from `allocator` at `loc`: the name's wide copy (`to_wide_string`; null is false), freed by a `defer`, and the value. `GetEnvironmentVariableW(name, null, 0)` first: 0 is false (unset, Fact 7); 1 is `""`, the zeroed string and true; else that many units from the heap (freed by a `defer`), asked again, and a result of 0, or not one less than the size, is false (the value changed in between); then `from_wide_string(units, allocator, loc)`. A name that isn't valid UTF-8 is false on Windows, with nothing allocated.
5. **Commands on Windows** (Task 3), through one Windows-only procedure in `environment.rig`, `run_through_shell :: (command: string, captured: *String_Builder, allocator: Allocator, loc: Source_Code_Location) -> int`, which `run_command` calls with a null `captured` and `run_command_with_output` with its heap builder, both after their zero-byte refusal and `c_fflush(null)`:
   - The shell is `%COMSPEC%` (through `get_environment("COMSPEC", HEAP_ALLOCATOR)`), or `cmd.exe` when it is unset or empty. The line, `"SHELL" /c COMMAND`, is built in a heap builder (quoted, so a shell path with spaces is one word; cmd reads only what follows `/c`, as from `system`, Fact 8), then made wide with `to_wide_string(line, allocator, loc)`, freed by a `defer`: the one allocation from `allocator`, as the C copy is today, so the counts of Fact 12 stay. Null (no memory, or a command that isn't valid UTF-8) is -1, nothing run.
   - `CreateProcessW(null, line, null, null, 1, 0, null, null, *startup, *information)`, `startup` with `C_STARTF_USESTDHANDLES`, the program's `GetStdHandle` input, output and error, the output replaced by the pipe's write end when capturing. The pipe: `CreatePipe` with an inheritable `C_Security_Attributes`, its read end made not inheritable (`SetHandleInformation`). After the call, the write end is closed in the program, then the read end is read with `ReadFile` into a `[4096]u8` on the stack, appended to `captured`, until it gives 0 or reads 0 bytes. `CreateProcessW` giving 0 is -1, both ends closed. Then `WaitForSingleObject(process, C_INFINITE)`, `GetExitCodeProcess`, every handle closed; the status is `cast(int) cast,trunc(s32) code` (Fact 8: `exit -1` is -1, as `system` gives it).
   - Linux keeps `system`, `popen`, `read` and `pclose`.
6. **What isn't UTF-8 on Windows after this.** A command's own output is what the command writes: cmd's `echo` writes the console's code page (Fact 9). The README and `environment.rig` say so in one sentence, in place of the caveat.
