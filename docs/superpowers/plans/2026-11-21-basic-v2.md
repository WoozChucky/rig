**Goal:** Basic's second part (#157): `print_error` and `print_error_string` to standard error, in order with standard output; `assert`, which names its caller's place and stops as a runtime error does, a failing one in a `#run` reported as a failing runtime check is; `sleep_milliseconds`; directories (`is_directory`, `make_directory`, `delete_directory`, `list_directory`) with UTF-8 paths on Windows; `run_command_with_output`; and `defer` in Basic's own code where it gives back on several paths. Each works on Windows and Linux, compiled and interpreted.

**Architecture:**
- **Basic** gains `assert.rig` and `directory.rig`, and grows `print.rig`, `time.rig`, `environment.rig` and `file.rig`. Where the two systems' C functions differ, `libc.rig` gets a top-level `#if OS == OS_WINDOWS { ... } else { ... }` that declares each system's functions under Basic's `c_` names (spec 4.9), and the procedures that call them choose with a statement `#if`. Windows' wide (UTF-16) calls are `kernel32`'s, which compiled and interpreted programs reach alike; the Universal C Runtime's `_write`, `_read`, `_popen`, `_fileno` and `_pclose` are used only with each other, never with a `FILE *` that C17's functions take (Fact 6).
- **Standard error** is written as a runtime error is (spec 8.1, 10.5): `fflush(NULL)`, then `_write` (Windows) or `write` (Linux) on descriptor 2. No `FILE *` for standard error on either system.
- **The compiler** gains one thing: Preload's `__runtime_error :: (text: string, message_start: int) #compiler;`, which lowering turns into the dynamic panic the IR already has (`panic %a, %b`, `ir.h:281-285`), in the program and in the compile-time world alike. So `assert` stops a compiled program with exit status 101, an interpreted one the same way, and a `#run` with `#run failed: runtime error: assertion failed: ...` and its calls (Q1).

**Tech Stack:** C-style C++23, built with the pinned clang 23.1.5 (`build.bat`, `build.sh`), no STL. Rig for Preload and Basic.

**Spec:** issue #157 (`gh issue view 157 --repo WoozChucky/rig`), a sketch its own text says is to be designed into decisions once its dependencies landed (they have: #147, #149, #150, #153, #154, #155, #156, and since then #152, #158, #159, #194, #197); `docs/rig-spec.md`, which Task 2 changes; `modules/Basic/README.md`, which every task changes. ## Questions for the maintainer

- **Q1. How does `assert` stop, and what does it do in a `#run`?** The issue says "exits with status 101, as a runtime error does". In the compiled program every option below writes the same line and exits 101; they differ while compiling.
  - **(a) Recommended: Preload's `__runtime_error`, a `#compiler` procedure lowered as a panic** (Decisions 4 and 5). A failing `assert` is a runtime error in every world: compiled and interpret mode alike (the same `.err`, Fact 2), and in a `#run` an error at the `#run`, `#run failed: runtime error: assertion failed: MESSAGE` with its calls, the build going on and reporting the rest (spec 7.8). Cost: one lookup in the checker, one branch in the call's lowering reusing the dynamic panic the IR, the backend and the interpreter already have (Fact 2), four unit tests, and five spec paragraphs. The name is Preload's own (`__`), usable by a program as `__save_command_line` is, documented for Basic.
  - (b) Basic alone: `print_error` the line, then C's `exit(101)`. No compiler change, and compiled and interpreted the same; but in a `#run` rig itself ends with status 101 at once, with no `#run failed`, no calls and no report of what else is wrong in the file (Fact 5), unlike every other failure in a `#run`.
  - (c) A built-in procedure of the language (`runtime_error(message, loc)`, predeclared as `array_add` is), lowered as (a) is. Public and checked like any built-in, but a language feature in a library issue: the built-ins' table is the resizable arrays' (`checker.h:1140-1166`, `Array_Builtin`), which it would have to generalise, and spec 2.5 and 3.17's lists change. Better as its own issue, if programs want it.
- **Q2. One PR or several?** Six tasks, each green on both hosts; Task 2 is the only one that touches the compiler.
  - **Recommended: one PR**, as the issue is one and every recent plan ships one PR per issue; each task is its own commit and its own review gate.
  - Or two: Task 2's compiler part (`__runtime_error`, its unit tests and spec) first, then Basic's five parts with `assert` in a second PR.
- **Q3. Windows' UTF-8 is directories' only.** The issue asks for directories through the wide functions; Basic v1's files, environment and `run_command` are ANSI (`file.rig:26-32`, `environment.rig:20-25`), so a program that lists `café_日本/` gets the UTF-8 names but can't open a file there with `read_entire_file` (Fact 8).
  - **Recommended: ship directories in UTF-8 as the issue says, say the gap in `file.rig`'s and `directory.rig`'s headers and the README, and file a follow-up issue** for UTF-8 throughout on Windows, whose two candidate designs it weighs: a UTF-8 active code page in a manifest every program links (the C runtime's ANSI calls become UTF-8, Windows 10 1903 and later; #152's plan, Q1 (c)), or Basic's files over `kernel32`'s `CreateFileW`/`ReadFile`/`WriteFile` (`_wfopen` can't serve while interpreted, Fact 6).
  - Or keep directories ANSI too (`CreateDirectoryA`, `FindFirstFileA`), consistent with v1 and as wrong for `日本`; or convert the files now, in this PR, which roughly doubles Task 4.
- **Q4. The directory procedures' edges.**
  - **Recommended:** `make_directory` is false when anything is already at the path (C's and Windows' own answer, and `is_directory` asks first); `list_directory`'s names sorted by bytes, in one allocation with a zero after each name (Decision 7), so its order is the same everywhere and one `free` gives it back.
  - Or `make_directory` true when a directory is already there (Jai's `make_directory_if_it_does_not_exist`); or the system's order (NTFS's is sorted without case, ext4's is a hash's), which a test can't print.
- **Q5. Text the issue left open.**
  - **Recommended:** `assert`'s line is a runtime error's, `PATH:LINE:COL: runtime error: assertion failed: MESSAGE` (spec 8.1's shape; in a `#run` the same MESSAGE after `#run failed: runtime error: `); and `run_command_with_output` reads in binary mode, the output's bytes as the command wrote them (`hi\r\n` from cmd's `echo`), as Basic's files are binary (`file.rig:5-8`).
  - Or `PATH:LINE:COL: assertion failed: MESSAGE`, without `runtime error:` (the issue's words, but then a `#run`'s MESSAGE and the program's line differ in shape); or text mode on Windows (`"rt"`, `hi\n`, Fact 7), which changes binary output and stops at Ctrl-Z.
