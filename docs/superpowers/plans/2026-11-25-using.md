# `using` on Fields and Parameters Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Jai's `using`, on a field and on a parameter. `Player :: struct { name: string; using entity: Entity; health: int; }` lets `p.position` mean `p.entity.position`, at any depth, `p.entity` still working; the field may be a pointer, `using transform: *Transform;`, reached through it (a null one stops the program at the use). `move :: (using e: *Entity, dx: float)` lets the body's `position` mean `e.position`, after locals and the other parameters and before globals; a value parameter's fields stay read-only. Two names at the same depth are `'position' is ambiguous: 'a.position' or 'b.position'`, at the use. A `*Player` converts implicitly to a `*Entity` through value `using` fields at any depth and offset, the pointer moved, null staying null. Literals name a struct's own fields only. Type information and `print` are unchanged; Preload's `Type_Info` kinds switch to `using info: Type_Info;`, so `t.size` works and `t.info.size` still does. Compiled, interpreted and in a `#run`; the debugger shows the fields as the ordinary fields they are.

**Architecture:**
- **Parser and AST:** `using` before a field's or a parameter's name sets `Ast_Field.is_using` or `Ast_Param.is_using`. `procedure_follows` takes `( using`. Elsewhere `using` stays a syntax error, with a message of its own where a statement or a declaration starts.
- **Types:** `Type_Field.is_using`, set by the layout. Nothing is flattened: the struct keeps one field for the `using` member, which type information, `print`, literals and the debugger see as an ordinary field.
- **Checker, fields:** a new walk, `check_find_member`, searches a struct's own fields (its anonymous members' included, as `type_find_member` does today), then the structs its `using` fields hold or point at, depth by depth, and returns the path or the two paths that make a name ambiguous. `check_member` builds the chain of members the path means, as it does for anonymous members, so a pointer is followed and null-checked by the existing code.
- **Checker, conversion:** `type_find_base` (types.cpp, pure) finds the value `using` fields through which a struct holds a `base`; `type_converts` takes `*Player` to `*Entity` when there is exactly one at the shallowest depth; lowering moves the pointer by the path's offset, keeping null.
- **Checker, parameters:** the procedure's `using` parameters are a lookup tier between the scopes and the top level. A name found there gets `Ast_Name.through`, the member chain it means (`e.position`), which places, `#run`'s walk and lowering follow instead of the name.

**Tech Stack:** C-style C++23, built with the pinned clang 23.1.5 (`build.bat`, `build.sh`), no STL; LLVM 23.1.5's C API; Rig for Preload and Basic; JavaScript (Node) for the VS Code extension's checks; gdb and cdb for the debugger tests.

**Spec:** GitHub issue #225 (`gh issue view 225`), whose Decisions are settled design; section 5 of the milestone's design, `docs/superpowers/specs/2026-11-22-milestone-5-type-system-design.md`, whose scope, non-goals (no `using` statement in a body), anti-goals and constraints bind every task; and `docs/rig-spec.md`, which each task updates for what it builds. It builds on C unions and anonymous members (#223, `docs/superpowers/plans/2026-11-24-unions.md`, whose `type_find_member` and member chains this extends) and tagged unions (#224, `docs/superpowers/plans/2026-11-25-tagged-unions.md`). ## Decisions this plan makes

1. **One PR, four tasks**, each green on both hosts, each a reviewer's gate:
   1. `using` fields: syntax, layout, lookup, literals; run tests (member chains need no new lowering).
   2. The pointer conversion and casts.
   3. `using` parameters, and the editor's grammar.
   4. Preload and Basic on `using`, type information, and the debugger tests.
2. **Representation.** `Ast_Field.is_using`, `Ast_Param.is_using`, `Type_Field.is_using` (set by `lay_out` from the field, cleared when Decision 4 refuses the type, so a refused field is an ordinary one and says nothing more). Nothing is flattened (the issue: the member is described as an ordinary field), so `Type_Info`, `print`, constant data, `#run` baking, C layout and the debug types need no change.
3. **Syntax.** `FieldDecl = [ "using" ] identifier ":" Type ";"` in a struct's, a union's and an anonymous member's braces; `Param = [ "using" ] identifier ":" [ ".." ] Type [ "=" Expression ]` in a declaration's signature. `procedure_follows` also takes `(` `using`, so `move :: (using e: *Entity) { }` is a procedure (no expression starts with `using`). Refused: among a tagged union's members (message above: a `using` there would reach a member outside a switch); before `union {`/`struct {` (the existing `expected a field's name, found 'union'`); in a procedure type (the existing `expected a type, found 'using'`: a type carries no `using`, which changes only a body's names); a `using` that starts a statement in a body (the design's non-goal) or a top-level declaration (message above; `parse_statement` and `parse_top_level_declaration`). Dumps: `(using entity Entity)`, `(using e (ptr Entity))`.
4. **What `using` takes:** a named struct or union, or one pointer to one. Anything else (`int`, an enum, `[2]Vec2`, `**Vec2`, a view, a procedure type) is `'using' needs a struct or a pointer to one, not 'T'`; a tagged union, or a pointer to one, is `'using' can't reach into a tagged union, 'Shape': ...`. A value field is checked in `lay_out`, a pointer field (a late field) where its type is made (`make_late_field`), a parameter in `check_signature`. A value `using` of the struct itself, directly or not, is the existing "contains itself"; behind a pointer it's allowed (Decision 6 ends the walk). A `using` parameter is allowed on any procedure, foreign ones included, as any parameter is: it changes only the body's names.
5. **Lookup through `using` fields** (`check_find_member`, Interfaces):
   - Depth 0 is the struct's own fields, its anonymous members' at any nesting included: spec 3.19 makes those the struct's own, and the declaration already refuses a clash among them (Decision 7). Depth d+1 is, for each struct searched at depth d, the struct each of its `using` fields holds (a value field's type) or points at (a pointer field's pointee), the `using` fields of its anonymous members included.
   - The first depth where the name is found decides. One path: it's the member. Two or more: `'x' is ambiguous: ...` at the name, naming the first two in walk order (field order, depth by depth). None at any depth: the existing `'Player' has no field 'nope'` (`member` for a union).
   - Before searching a struct it enters, the walk lays it out (`check_layout`; a pointer field's pointee may not be yet) and makes a pointer `using` field's type (`check_late_field`); a field whose type is still unknown (a struct under way, an error) is skipped.
   - The walk ends on cycles and stays small: a struct searched at an earlier depth isn't searched again (it held no match there, and what it reaches was queued then), and at one depth a struct is searched through at most two paths (two are enough to say a name is ambiguous). So `Node :: struct { using parent: *Node; }`, `A`/`B` pointing at each other, and forty levels of two `using` pointer fields each end at once.
   - `check_member` turns the path into the chain of members it means, as it does for anonymous members today: one `Ast_Member` per field on the way, at the name written (`pos`), `start` the operand's, named as the field (empty for an anonymous member), its `index` and type; the struct for the next index is the field's type, or its pointee when it's a pointer. So `s.x` through `using transform: *Transform` is `s.transform.x`: lowering, places (a field through a pointer is always a place), the null check (at the name written), `#run`'s walk and constant folding (`K.position.y` of a constant) work unchanged.
6. **Anonymous members and `using`, decided consistently.** Names reachable twice through anonymous braces stay refused where declared (C's rule, #223); names reached through `using` are never checked at the declaration, only at the use (the issue's rule). An own or anonymous member's field hides a `using`-reached one of its name (depth 0 against depth ≥ 1); two `using`-reached ones at one depth are ambiguous at the use, whether either sits inside an anonymous member or not. `lay_out`'s `reachable` check and `held_under_way` keep calling `type_find_member`, which doesn't follow `using` fields.
7. **Literals name a struct's own fields** (and, as today, its anonymous members'): `place_named_values` keeps `type_find_member`; a name it doesn't find that `check_find_member` does is `a literal can't name 'position', reached through 'entity'; ...` instead of "has no field". Values in order go to the own fields in order, the `using` field taking its struct: `Player.{"ann", .{1, .{1, 2}}, 3}`.
8. **The conversion** (`type_find_base`, Interfaces): `*S` converts implicitly to `*B` when S holds a B through value `using` fields only, anonymous members on the way included, never through a pointer field (the issue). The shallowest depth that has one decides (the struct's own `using` fields are depth 0); two at that depth make it ambiguous. `type_converts` takes it when there is exactly one; `check_convert` (and `check_cast`, Decision 9) says the ambiguity, then returns true with the value's type cleared, as a literal's error does, so nothing more is said. Since `type_converts` is pure, `check_convert`, `check_unify_pointers` and `check_multi_assign` call `check_layout` on a struct pointee before asking it (bodies normally find every layout done, Fact 5; a body a `#run` reaches during the layouts may not). So it applies wherever a value goes into a known type: a declaration, an assignment, an argument (a `..*Entity` one too), a return, a literal's field or element, a default value, a multi-assign, and a comparison's operands (`pe == *p`).
   - **Lowering:** `convert_base_pointer` (Interfaces) in `lower_value`'s last line, in `lower_multi_assign` (which uses `resize`, Fact 9) and in `lower_cast`. An offset of 0 emits nothing; otherwise `select(p == null, null, ptradd(p, offset))`: null stays null, as C++ keeps it in a base conversion, so a null `*Player` passed as a `*Entity` is still caught by the null check at its use, not turned into address 16. A constant (`null` cast to `*Player`) stays the constant.
   - **Not converted:** by value (`Entity` from a `Player`; the issue gives the pointer only), from `*Entity` back to `*Player`, `**Player`, `[]Player`, `[..]Player`, procedure types.
9. **Casts.** `cast(*Entity) p` is the conversion, moved and null-kept, by spec 3.14's first row ("a type it converts to implicitly: the implicit conversion"); an ambiguous one is the same message at the cast's value. Every other pointer cast stays the same address: `cast(*Player) pe` included (round-trips only when the `using` field is at offset 0, which the spec says), and `cast(*Entity) cast(*void) p` reinterprets on purpose. No existing program changes: nothing has a `using` field today.

## Not in this plan

- `using` as a statement in a body (`using e;`), on a global or a local, and `using` of an enum or a module to bring its names into scope: the design's non-goal.
- Converting by value (`Entity` from a `Player`), Jai's `#as`, and moving a pointer back (`*Entity` to `*Player` by the field's offset): a cast of those stays the same address.
- Converting views, arrays, resizable arrays, pointers to pointers and procedure types through `using`.
- `using` in a procedure type, and a `using` flag in `Type_Info_Struct_Member`.
- Debugger names for fields reached through `using` (`p.position`, a bare `position` in a `using` procedure), unless Q1 says (b).
- `using` on a tagged union's member, and reaching into a tagged union.
- `using` in generic structs and with `$T` (#226 and #227 meet it there).
- Rewriting Basic's tables generically (section 10 of the milestone).
