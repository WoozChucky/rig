# Rig: language and toolchain design

Status: approved by Nuno, 2026-11-11.

Rig is a new compiled programming language, built as a learning project that follows the path a real language takes, modelled on Jonathan Blow's Jai. This document records what was decided in the design conversation. Each decision is marked: **(Nuno)** is the owner's own decision; **(Claude's call)** is a default proposed during the conversation and not objected to, which the owner may still change while reading.

## 1. Intent

- **Educational.** Nuno wants to learn how a programming language is actually made, by building parts of it himself with guidance, while the result is a real, usable compiler, not a toy interpreter. (Nuno)
- **As close as possible to what creating a language really is**, following Jai's path: a C++ compiler, compile-time execution, the build system written in the language, an LLVM backend for release builds and its own backend for fast debug builds. (Nuno)
- **Philosophy** (Nuno): software today is bloated; the language gives the programmer control. No hidden machinery, nothing the developer didn't choose, no external build systems or tools. The language doesn't protect programmers from themselves (no borrow checker, no garbage collector), but it tells them when they got something wrong.
- What annoys Nuno in C/C++ and Rig fixes (Nuno): header files and build systems; undefined behaviour; very slow compilation even with PCH and incremental builds; no standard way to get dependencies; bad error information and crashes that don't explain themselves; a standard library that is neither readable nor fast.

## 2. Goals, non-goals, anti-goals

**Goals**
- Native 64-bit executables on **Windows x64 and Linux x86-64**, first-class. (Nuno)
- Fast compilation by design: a whole program compiles from scratch quickly, so no incremental builds or precompiled headers are needed. (Claude's call, following Jai)
- No undefined behaviour: every operation has a defined meaning (section 6.4). (Nuno)
- First-class C interop (section 5). (Nuno)
- One command for the whole toolchain: compile, run the build file, fetch dependencies, run tests, serve the language server. (Nuno)
- Good diagnostics: precise positions, errors that point at the real problem; crashes and failed checks print what happened and a stack trace. (Nuno)

**Non-goals**
- 32-bit targets, old or unusual platforms. (Nuno)
- Camelot (Nuno's RISC-V OS) as a target for now. It may come later. (Nuno)
- An own debugger. Rig emits debug information; existing debuggers are used. (Nuno)
- Self-hosting is a long-term possibility, not a commitment. (Claude's call; Jai isn't self-hosted either)

**Anti-goals** (would make this a failure even if it works)
- A garbage collector, a VM, bytecode at run time, or an interpreter running user programs at run time. (Nuno)
- Exceptions / try-catch. (Nuno)
- Smart pointers or ownership/borrow checking forced on the programmer. (Nuno)
- An external build system for Rig programs (make, CMake). (Nuno)
- Builds that touch the network (section 8). (Nuno)
- Classes, inheritance, virtual functions. (Nuno)

## 3. The toolchain

- **Name:** Rig. Command `rig`, source files `.rig`, e.g. `rig build hello.rig`. (Nuno) An existing Rust LLM library and an old Unix tool share the name; neither is a language. A web search for other uses was offered and not yet done.
- **One command, `rig`**, with subcommands: `build`, `run` (Claude's call), `check` (the diagnostics alone, writing nothing: what editors run until `lsp`), `test`, `get`/`fetch`, `lsp`, later `fmt`. (Nuno: one command for everything; subcommand names are Claude's call)
- **The compiler is written in C++**, as Jai's is. (Nuno)
  - **C-style C++, no STL** (Nuno): structs, functions and a few templates; the compiler's own arena allocator, growable array, string view and hash table; no exceptions, no RTTI.
  - **C++23** (Nuno), compiled with **clang** on both platforms (Nuno). On Windows, clang targets MSVC and uses Visual Studio's headers, libraries and linker (Visual Studio 18 and clang 23.1.4 are installed on Nuno's machine). gcc on Linux should also work (Claude's call).
  - **Unity build**: `build.bat` (Windows) and `build.sh` (Linux) each compile one `.cpp` that includes all the others. No CMake. (Nuno)
- **Backends** (Nuno), Jai's way:
  - **LLVM** for optimised release builds, and at first for all builds.
  - **Rig's own x86-64 backend** for very fast debug builds, later (milestone 8).
  - Both translate **Rig's own IR** (intermediate representation), never the source, so adding a backend never touches the front end. (Claude's call)
  - **An IR interpreter inside the compiler** runs compile-time code (`#run`, the build file). (Claude's call, required by the compile-time decisions)
- **LLVM is linked into the compiler statically**, through LLVM's **C API (`llvm-c`)**, not the C++ API: stable between versions, plain C, fits a no-STL compiler. (Claude's call; Nuno rejected writing `.ll` text and invoking clang, since the toolchain must not depend on external tools of that kind)
  - The installed LLVM on Nuno's machine has only `LLVM-C.lib`/`LLVM-C.dll` and the C headers, no static libraries. So: LLVM's **official prebuilt release archive of the same version (23.1.4)**, with static libraries, unpacked into a folder the build scripts point at, never committed. The version is pinned; changing it is a deliberate change. Building LLVM from source only if the archive lacks something. (Claude's call)
- **Linking, Jai's way** (Nuno, "Jai's way"; the details checked against Jai's documented link commands):
  - **Windows:** Microsoft's linker, `link.exe`, found the way Jai finds it (Jonathan Blow's MIT-licensed `microsoft_craziness.h` approach: locate Visual Studio and the Windows SDK), with LLVM's `lld-link` as the fallback. Either way the MSVC and Windows SDK libraries (the C runtime) must be installed, as for Jai; the Visual Studio Build Tools are enough.
  - **Linux:** LLVM's `lld`, shipped with the toolchain, as Jai ships its own `lld` there, linking against the system's glibc and its start files (`crt1.o`, `crti.o`, `crtn.o`).
  - `lld` comes from the same pinned LLVM release archive. (Claude's call)
- **Debug information is first-class** (Nuno): **PDB on Windows, DWARF on Linux**, so Visual Studio, WinDbg, RemedyBG, the RAD Debugger, gdb and lldb work. Arrives in milestone 2.
  - How: the compiler builds the debug info with LLVM's C API (`llvm-c/DebugInfo.h`). On Windows it sets the `CodeView` module flag, so LLVM writes CodeView records into the object file, and **the linker makes the `.pdb`** (`/DEBUG`). On Linux LLVM writes DWARF into the object (the `Dwarf Version` module flag). Rig's own x64 backend will have to write CodeView and DWARF itself. (Claude's call)
- **Language server:** `rig lsp`, a subcommand reusing the compiler's front end (Nuno). Consequence now: the front end **recovers from errors** (keeps parsing and checking the rest of a broken file) and keeps precise positions, from day one. (Claude's call, agreed in principle by Nuno)
  - How: after a syntax error the parser skips to the next declaration, keeping the broken one's name when it still looks like a declaration of that name: a mistyped or missing `::` (`greet : () {`, `greet () {`, `greet := () {`, `greet = () {`) or a stray token before it (`greet * :: () {`). A name followed by `(` but no `::` counts only when the parentheses are a signature's: the `)` that closes them, on whatever line, is followed by a `{`, `->` or directive. A stray call (`foo("x");`, or `foo("x")` with its `;` missing) is followed by something else and names nothing, since naming it would hide the unknown `foo`. Stray tokens in front of a name (`*greet :: () {}`) are skipped, and the declaration after them is parsed whole. The checker runs anyway: that name is declared with an unknown type, so nothing is reported about it or its uses, and every other declaration is checked. A broken declaration with no name could have been `main`, so a missing `main` isn't reported then. One mistake gives one message. (Claude's call)

## 4. Runtime and the C library

- **Jai's way** (Nuno): every Rig program links the platform's **C runtime** (Microsoft's on Windows, glibc on Linux, dynamically). Rig's standard library reaches the OS through C functions (files, processes, time, ...) declared as foreign functions.
- **The default heap allocator is Rig's own,** as Jai's is: on x64, Jai's default allocator is its own (a cut-down rpmalloc written in Jai), not the C library's `malloc`. Rig gets a general-purpose allocator written in Rig, in the `Basic` milestone; until then the context's default allocator calls `malloc`. (Claude's call, following Jai)
- Rig's own **native support layer** (like Jai's `Runtime_Support`): program startup, the context, assertions, stack traces. Ordinary compiled code linked into the program; nothing runs that the program didn't call. (Claude's call)
- Programs are **not** required to be single self-contained files, and the toolchain is not required to be a single binary that needs nothing else installed. (Nuno: "no need for the single binary anymore"; "one command for everything" stays)

## 5. C interop (first-class) (Nuno)

- Calling C functions: `#foreign` declarations, the platform's C calling convention exactly (Windows x64 convention on Windows, System V AMD64 on Linux).
  - "Exactly" means as clang does it, including what the ABI documents leave unsaid: on Linux an `s8`, `u8`, `s16` or `u16` argument or return value is widened to 32 bits, sign-extended if its type is signed and zero-extended if unsigned (LLVM's `signext`/`zeroext`), which clang-built C code relies on; on Windows it isn't, the receiving side widens it. Rig's own procedures follow the same rule, so a call and its callee always agree. (Claude's call)
- Being called by C: procedures marked C-callable (callbacks), which set up a context before calling ordinary Rig code (section 6.6).
- C-compatible layout of structs, unions, enums and pointers that C sees.
- Linking C libraries: static (`.lib`/`.a`) and dynamic (`.dll`/`.so`).
- **C libraries come in as modules, Jai's way** (Nuno: "importing the raylib module from my language"): a module holds declarations generated once from the C headers by a **bindings generator** (committed, so nobody parses headers at build time) plus, for a third-party library such as raylib, its prebuilt files. `#import "raylib"` brings both in. A module for an OS library (the Windows API, OpenGL) holds only declarations and names the system library (Jai's `#system_library "kernel32"`), with nothing prebuilt. How the bindings generator parses headers is open (section 12); Jai's uses libclang, which the pinned LLVM archive includes.

## 6. The language

All of section 6 is **Jai's way** by Nuno's decision unless marked.

### 6.1 Syntax
- `name : type = value;`, `name := value;` (inferred), `name :: value;` (constant). Procedures, structs and constants are declared the same way: `square :: (x: int) -> int { return x * x; }`, `Vec2 :: struct { x: float; y: float; }`.
- `for 0..9 { ... }` (both ends included: ten iterations) with `it` (and `it_index`), or a named iterator `for i: 0..9`; `if` and `while` without parentheses (optional, as in Jai); semicolons. The grammar can be parsed without knowing which names are types.
- Milestone 2a's details (Claude's calls, from its plan): binary operators bind as in Go, loosest first `||`, `&&`, comparisons, `+ - | ^`, `* / % << >> &`, all left-associative (so `x & 1 == 0` means `(x & 1) == 0`, unlike C); then the prefix operators `- ! ~ cast`, then calls. The bodies of `if`, `else`, `while` and `for` are always blocks in braces. Conditions are `bool`; an integer isn't one. Parameters are read-only: copy one into a variable to change it. A name declared in a block is visible from its declaration to the block's end; an inner block may declare it again, hiding the outer one, the same block may not. Parameters are in the body's own block, so a local can't take a parameter's name (`f :: (a: int) { a := 1; }` is "'a' is already declared"), rather than hide it. `for a..b` evaluates both ends once, `a` first, and runs for every value from `a` to `b`, none when `a > b`, correctly at a type's limits (it stops after `b` without computing `b + 1`); the ends meet at a type as an arithmetic operator's operands do, and untyped ends make an `int` iterator. `it` and `it_index` (an `int` from 0) are read-only and belong to the body's block, as parameters do to a procedure's; a named iterator (`for i: 0..9`) is declared instead of `it`, so inside it `it` is an outer loop's, if any; a named iterator can't be called `it_index` (`a loop's iterator can't be called 'it_index'`). A `for` over anything but a range waited for milestone 2b's arrays (6.5); a name followed by anything but `..` or the body is an iterator missing its `:` (`for i 0..9`, `for x in 0..9`: `expected ':' after the iterator's name, as in for i: 0..9`), and anything else after the first expression is `expected '..' or the loop's '{'`. `break` and `continue` act on the innermost loop; `continue` in a `for` goes on to the next value. `bool` is its own type, not an integer: comparisons give one, `== !=` also compare two bools, `&& || !` take bools, and `&&`/`||` evaluate their right side only when the left doesn't decide; a `bool` is C's `_Bool` to foreign procedures. A procedure that returns a value must not reach the `}` of its body: a block reaches its end unless its last statement is a `return`, a block that doesn't reach its own end, an `if` with an `else` neither of whose branches does, or a `while` whose condition is the constant `true` and that has no `break` of its own; an `if` or `while` whose condition is an error counts as not reaching its end, so the condition's message is the only one. Procedures are declared only at the top level, for now.
- Globals and top-level constants (Claude's calls, milestone 2a): a global variable is declared at the top level as a local one is (`counter : int;`, `start := 5;`), and a constant too (`LIMIT :: 100;`). Both are visible everywhere, in any order, and share their names with the procedures (`'x' is already declared at ...`); a local may hide one. A global's value must be known while compiling, for now (`a global's value must be known while compiling, for now`), since it's written into the program's file; a string literal is too, its address written into the global by the linker (milestone 2b; until then it was `global variables can't hold a string literal yet; assign it in a procedure`); without one, or with `---`, it starts at zero, as a global is never on the stack. Globals and constants are worked out where they're first needed, so `A :: B + 1; B :: 2;` makes `A` 3; a value that needs itself, directly or through others, is `'A' is defined in terms of itself`, at the name being worked out, once per circle, a circle through a declaration already found in one saying nothing more (nor is anything said about the circles' declarations, typed or not). After `::` at the top level, `()` or `(name:` begins a procedure, and any other `(` a constant's value, so `N :: (1 + 2);` is a constant.
- A limit of the compiler (Claude's call, milestone 2a): an expression nests at most 1000 levels deep, each parenthesis, prefix operator, cast, call and binary operator a level above what it holds (so a chain of 1000 `+` is 1000 levels), and blocks at most 1000 deep, a procedure's body the first. Deeper ones are `this expression is nested too deeply (more than 1000 levels)`, at the expression's start, and `blocks are nested too deeply (more than 1000 levels)`, at the `{` one too many, rather than a crash: the compiler walks the tree recursively, on a stack of a fixed size. A type nests at most 1000 levels too, each `*`, `[]` and `[N]` a level (issue #54). Types and expressions nest inside each other, and their levels count together against the one limit of 1000: an array's count is read inside its `[N]` level, and `size_of` and `cast` read their type a level down (so `[size_of([size_of(u8)]u8)]u8` is 4 levels, and 500 such pairs are the most), though `size_of(T)` itself is no level of the expression around it. The level one too many is `types are nested too deeply (more than 1000 levels)` at its `*` or `[`, or the expression's message when it's an expression's. The limit is on the types a program writes: a type the compiler infers has none (each `p2 := *p1;` is a pointer a level deeper than the last), and the compiler names one in a message however deep it is. An else-if chain has no limit to its length, though its tree nests one level per arm: every stage walks a chain in a loop, arm by arm, so a generated chain of thousands of arms compiles (issue #54).

### 6.2 Code organisation
- Structs and free procedures. Composition through `using`. No methods inside structs, no classes, inheritance or virtual functions. Interfaces, where wanted, are structs of procedure pointers or generic procedures.

### 6.3 Files and modules
- `#import "Name";` brings in a module (a directory of code); `Name :: #import "Name";` names it. `#load "file.rig";` adds a file to the program. No headers; declaration order is free. Everything is visible unless a file marks part of itself private (`#scope_file`, `#scope_export`).

### 6.4 Types, integers and undefined behaviour
- `s8 s16 s32 s64`, `u8 u16 u32 u64`, `int` = `s64`, `bool`, `float32`, `float64` (`float` = `float32`).
- Widening conversions are implicit; narrowing needs `cast`. Narrowing casts that lose information are checked at run time in debug builds.
- Milestone 2a's details (Claude's calls, from its plan):
  - Integer constants are untyped until they meet a type, and must fit it (`x : u8 = 300;` is an error); alone they're `int`. Arithmetic on untyped constants is exact within `int`'s range. A literal above `int`'s range is a `u64`.
  - No integer promotion: `u8 + u8` is a `u8` and wraps at 8 bits. Mixed types widen when one converts implicitly to the other (same sign and wider, or unsigned into a wider signed); otherwise, as for `u32 + s32`, a `cast` decides. `int` and `s64` mixed give the left operand's type. A shift has its left operand's type (an `int` when that's an untyped constant and the amount isn't a constant); its amount may be any integer type, and is masked to the left operand's width, in constants too.
  - `-9223372036854775808` is `int`'s most negative value: the literal alone is above `int`'s range, so a `u64`, but `-` applied directly to it gives the untyped constant. `-` applied directly to a larger literal (`-9223372036854775809`) is an error, `constant overflows 'int'`, as in Go, rather than the `u64` wrapped to a positive number. A constant `N :: e;` is a number (an integer or a float) or a `bool`, for now (only they fold), untyped when `e` is an untyped constant; constants of a type (a cast of a constant, a `u64` literal) fold with that type's wrapping, as at run time.
  - `cast(T) x` is checked (the value must be the same number in `T`); `cast,trunc(T) x` is C's conversion, keeping the low bits, unchecked: the way to wrap on purpose. A float cast to an integer truncates and saturates (the rule below), unchecked.
    - A cast is a prefix operator, like `-` (`cast(u8) a / b` is `(cast(u8) a) / b`); its only modifier is `trunc` (`unknown cast modifier 'foo'; the one there is is 'trunc'`).
    - Between integers, `cast` checks at run time, failing with `runtime error: the value doesn't fit in 'T'` at the cast: narrowing, the value truncated and extended back by `T`'s sign must be the value again, and from an unsigned type to a signed one the narrowed value must also not be negative (a `u16`'s 65535 truncates to an `s8`'s -1, which extends back to 65535); the same width with the other sign, the sign bit must be clear; widening from signed to unsigned, the value must not be negative; any other widening needs no check. A constant that doesn't fit is a compile error, `300 doesn't fit in 'u8'`, and one that fits is a constant of `T`.
    - `cast,trunc` takes integers only (`cast,trunc only takes integers`): narrowing keeps the low bits, widening extends by the source's sign, the same width keeps the bits. Constants fold the same way: `cast,trunc(u8) 300` is the `u8` constant 44.
    - A `bool` casts to an integer as 0 or 1. Nothing casts to `bool` but a `bool`: a number is `can't cast 'int' to 'bool': compare instead, as in x != 0` (`'float32'` for a float). Anything else casts only to the type it converts to implicitly, its own (or a string literal to `*u8`); otherwise `can't cast 'A' to 'B'` (milestone 2b adds pointers' casts, 6.5).
  - `/` and `%` truncate toward zero, `%`'s sign the dividend's, as in C; the most negative value divided by -1 wraps to itself, remainder 0. A constant divisor of 0 is a compile error, `division by zero`, at the operator (`x /= 0` too). Constants fold: untyped ones exactly (`int`'s most negative value `/ -1` is `constant overflows 'int'`), typed ones wrapping as at run time.
    - At run time a divisor not known while compiling is checked, failing with `runtime error: division by zero` (for `%` too) at the operator. A signed divisor that may be -1 is replaced by 1 when it is, and the quotient by `0 - x`, with LLVM's `select` rather than a branch, so no `sdiv` or `srem` ever sees the case x86 traps on. A constant divisor needs neither: by -1 the result is `0 - x` or 0 without dividing.
  - A runtime error prints `PATH:LINE:COL: runtime error: MESSAGE` to stderr and exits with status 101, on every system. It flushes C's output streams first (`fflush(NULL)`), so what the program printed before the error comes out before the message, even where stdout and stderr meet (`prog 2>&1`). `PATH` is the source file's path as `rig build` was given it. The program writes the message with C's `write` (`_write` on Windows) in one call, from a routine of the runtime that each module that can fail defines for itself; a program's own `write`, `fflush` or `exit` doesn't get in its way. Nor does a program's own `memmove`, `memset` or `memcpy` take the calls LLVM makes to C's to copy and zero memory, or its own `__chkstk` the stack probe LLVM calls on Windows for a frame bigger than a page.
  - Strings, in milestone 2a: a string literal converts implicitly to `*u8` (its bytes end with a zero, so C can read them), but a variable couldn't hold a `string` until milestone 2b (6.5).
  - Floats (milestone 2a's last part):
    - `float32` and `float64` are IEEE 754's single and double precision, C's `float` and `double` (a foreign procedure takes and returns them as those). `float` is `float32` itself, the same type under a second name, so messages say `float32`.
    - A float literal is an untyped float constant; alone it's a `float32` (`x := 1.5;`, Jai's default). Untyped constants fold in double precision, an untyped integer among them converted to a double (`1 + 0.5` is the untyped float 1.5); an operation on finite operands whose result overflows a double is `constant overflows 'float64'` (`1e300 * 1e300`), as untyped integers overflow `int`, a division by zero excepted. One meeting `float32` must be within its range, `1e+300 doesn't fit in 'float32'` (the value as C's `%g` writes it), and is rounded to it, once: a literal as written (or `-` before one, or a constant named for one) from its decimal text, as C's `strtof` reads it, not by way of the nearest double, so it fits unless that rounding gives an infinity, and an integer straight to the `float32` (Claude's call; arithmetic on untyped constants is still done in double, and its result rounded); infinity and NaN, which a division by zero gives (`1.0 / 0.0`, `0.0 / 0.0`) and arithmetic on them keeps, are `float32` values too. A typed float constant folds as at run time, a `float32`'s result rounded to `float32`.
    - An untyped integer constant converts to a float type where it meets one (`f * 2`, `x : float64 = 3;`). `float32` widens to `float64` implicitly. Nothing else converts implicitly between integers and floats, or from `float64` to `float32`: `a value of type 'int' doesn't convert to 'float32' implicitly`; mixed in an operator, `mismatched types 'float32' and 'int' for '+'; cast one of them`.
    - `+ - * /` and unary `-` take floats, with IEEE 754's arithmetic exactly (no fast-math): a division by zero is an infinity, or NaN for `0 / 0`, never an error or a check, even with a constant divisor. `%`, the bitwise operators, shifts and `~` take integers only: `'%' needs integers, not 'float32'`. An operator that takes floats says so when given something else: `'+' needs numbers, not 'bool'`, `'-' needs a number, not 'bool'`.
    - Comparisons are IEEE 754's: ordered, so false when either side is NaN, except `!=`, which is true then (NaN != NaN). `-0.0 == 0.0`.
    - Casts: float to float rounds to nearest (`float32` to `float64` is exact); integer to float rounds to nearest (16777217 as a `float32` is 16777216); float to integer, `cast(T)`, truncates toward zero and saturates at `T`'s limits, NaN giving 0, with no runtime check: LLVM's `fptosi.sat`/`fptoui.sat` (the rule below), rather than a check that the number survives, since every float has an answer. A cast of a constant folds by the same rules: `cast(s32) 1e30` is the constant 2147483647, not an error, and `cast(float32) 1e300` is infinity (an untyped float operand is a `float64` first, an untyped integer an `int`). `cast,trunc` takes integers only. (Claude's calls)
- **How far "no undefined behaviour" reaches: Jai's realistic approach** (Nuno chose option B over a strict guarantee that would slow release builds and deny LLVM most optimisations):
  - **Always defined, in every build, optimised or not** (Claude's rules, accepted by Nuno):
    - integer overflow wraps (two's complement): the compiler never gives LLVM `nsw`/`nuw`;
    - integer division by zero (`/` or `%`) never goes unnoticed: a constant divisor of 0 is a compile error, and any other divisor is checked before the division, which crashes with a message when it's 0; a float divided by zero is IEEE 754's, an infinity, or NaN for `0 / 0`, and no error;
    - a shift amount wraps to the type's width (x86's behaviour; LLVM would treat it as undefined, so the compiler masks it);
    - a float converted to an out-of-range integer gives a defined result (saturating, LLVM's `fptosi.sat`/`fptoui.sat`) (Claude's call);
    - **variables start zeroed** unless declared uninitialised on purpose (Jai's `---`), so a forgotten initialisation is never undefined. Reading an on-purpose-uninitialised variable before writing it gives an unspecified value. (Claude's call, from Jai)
  - **Caught in debug builds:** null dereference (always crashes with a stack trace), out-of-bounds access (bounds checks), use-after-free and double free (the memory debugger, section 6.6), narrowing casts that lose information.
  - **The programmer's responsibility in release builds with the checks off:** a memory error there (null or dangling pointer, out-of-bounds access, pointer arithmetic outside an object, a data race between threads) may do anything, as in C. Two memory errors aren't caught in any build yet (Claude's call, milestone 2b): writing a string literal's bytes, which are read-only memory, and using a view or pointer of a procedure's local or temporary after it returns; the memory debugger (6.6) is where the second could be caught. The compiler may give LLVM the usual memory assumptions (`inbounds`, non-null where proven) in optimised builds.
  - The IR, the interpreter and the future x86-64 backend all follow these same rules.
- Floating point: strict IEEE 754, no fast-math unless asked for.

### 6.5 Pointers, arrays and strings
- `*T` pointers, `.` through pointers, pointer arithmetic, any pointer may be null.
- `[N]T` fixed arrays, `[]T` views (pointer + count), `[..]T` growable arrays that remember their allocator (`array_add`, ...).
- `string` is a view of bytes (pointer + length), not zero-terminated. Helpers convert to C strings.
- Bounds checks on by default; can be switched off for a build or locally.
- Milestone 2b's details (Claude's calls, from its plan, `docs/superpowers/plans/2026-11-12-milestone-2b-structs-pointers-arrays-strings.md`):
  - **Pointers**, Jai's syntax: `*x` is x's address, `p.*` what p points at, `null` the pointer to nothing. `*x` binds as `-` does and `p.*` as a call does, so `*p.*` is `*(p.*)`; a `*` right after a `.` is a token of its own, so `p.*=5` assigns through p and `p.*==q` compares. Only a variable, a field or an element has an address, and only they can be assigned to (`only a variable, a field or an element has an address`, `... can be assigned to`); a parameter doesn't (parameters are read-only, 6.1), nor a constant or a loop's iterator. `*void` converts implicitly to and from every pointer type and can't be dereferenced or used in arithmetic; no other pointer converts to another without a cast. `p + n`, `n + p` and `p - n` move by `n` of what p points at, as in C (`'+' moves a pointer by an integer, not 'float32'` otherwise); `p - q` is an `int`, the distance in those; pointers compare (`<` as unsigned addresses); nothing about them is checked but a dereference of null: `p.*`, `p.x` and `p[i]` stop with `runtime error: null pointer dereference`, checked where the place is worked out, before anything is read or written through it. So is a view's or a string's data, the pointer they read through, when it's null and the count says there are elements (set by hand, or from a failed allocation): `v[i]` once the index is inside, `for v` once before its first iteration, at the sequence, and `a == b` on strings when the two counts are the same and above 0 (the only time it reads bytes), at the operator; a zeroed view, count 0, reads nothing and passes. A pointer casts to any pointer, and to and from `int`, `s64` and `u64`; `null` casts only to a pointer, and stays a constant. `size_of(T)` is T's size, an untyped constant: `size_of` followed by `(` is the built-in, whose argument is a type. `void` is a type only behind a pointer. `null` is a constant, so a global pointer may start as one; alone (`x := null;`) it has no type (`null needs a pointer type, as in p : *int = null;`). `p - q` on pointers to a type of size 0 (an empty struct, `[0]int`) is an error, `can't subtract pointers to 'Empty': it has no size`. A misaligned pointer (from a cast) is a memory error, the programmer's responsibility as in 6.4's list. A `bool` in memory is a byte, C's `_Bool`: any nonzero byte reads as `true`.
  - **Structs** are declared at the top level only, for now (`Vec2 :: struct { x: float; y: float; }`), in any order, and laid out as C lays them out (each field at the next multiple of its alignment, the size rounded up to the largest alignment). A struct can't hold itself, directly or through others (`'Node' contains itself; it can hold a pointer to itself, *Node`), only what lies elsewhere: a pointer to itself, or a view of itself, through arrays too (`*Node`, `[]Node`, `[2]*Node`, `[][2]Node`, `*[2]Node`). A struct whose size needs itself through a global or a constant (an array's count, `S :: struct { a: [g.count]int; } g : [2]S;`) holds no copy of itself, and is told so as a global is (`'S' is defined in terms of itself`). `e.x` reaches a field through a struct or one pointer to it. Literals are Jai's: `Vec2.{1, 2}` in order, `Vec2.{y = 2}` by name, the fields not given zeroed, and `.{1, 2}` takes its type from where it's used. Structs copy on assignment, as arguments and as results, and aren't compared; every value is read before anything is written, so `v = Vec2.{v.y, v.x};` and `g1, g2 = f();` with `return g2, g1;` swap. Field defaults and `using` (6.2) wait for milestone 5. The rulings and their messages:
    - Declared anywhere but the top level: `structs can only be declared at the top level, for now`. A field is `name: type;`; anything else where a field goes is `expected a field's name, found '('` (or whatever it found), and a body that runs into the next declaration `expected '}'`. Two fields of one name: `'x' is already declared at PATH:L:C`. The circle's message is at the struct whose layout was being worked out when it closed, once per circle.
    - A struct's name is a type: as a value, `'Vec2' is a type, not a value`, and so is a built-in type's (`x := int;` is `'int' is a type, not a value`, not an unknown identifier; called, `'s64' isn't a procedure, so it can't be called`); a name declared as anything else, where a type goes, `'foo' is not a type`. A built-in type's name always means the built-in type, so a struct can't take one (`u8 :: struct { ... }` is `'u8' is a built-in type`, at its name).
    - `e.x` on anything but a struct or a pointer to one (one pointer: `**Node` needs `.*` first): `'.x' needs a struct or a pointer to one, not 'int'`; a field it doesn't have: `'Vec2' has no field 'z'`; both at the field's name. A field is a place when its struct is one, or always through a pointer.
    - A literal's type is the name before its `.`, never one in parentheses (`(Vec2).{1}` is `expected a field's name, found '{'`, as `f().{1}` is). A literal's values are all named or all in order (`a struct literal's fields are all named or all in order, not both`); `'Vec2' has 2 fields, but this literal gives 3`; `field 'x' is given twice`; `T.{` needs a struct (`a '.{' literal needs a struct type, not 'int'`), and so does `.{` where it's used. `.{` with nothing to take a type from (`x := .{1, 2};`, an operand): `this literal's type isn't known; write it before the '.', as in Vec2.{1, 2}`.
    - `==` and `!=` take numbers, bools, pointers and strings only (`'==' needs numbers, bools, pointers or strings, not 'Vec2'`); no other operator, and no condition, takes a struct.
    - A global struct's value is a literal of constants (nested literals' too); the first value that isn't is `a global's value must be known while compiling, for now`. A constant can't be a struct.
    - A foreign procedure takes and returns no struct (`a foreign procedure can't take a 'Vec2' yet; pass a pointer to it`, `a foreign procedure can't return a 'Vec2' yet`).
  - **Arrays and views**: `[N]T` (N a constant), `[]T` a view, `{ count: int; data: *T; }` in that order (Jai's), so `string` is one too. An array converts implicitly to a view of it (of the array itself, when it has an address, so a procedure taking `[]int` can sort the caller's array, else of a temporary, one per place in the source, valid until its procedure returns, which the array is copied into once it is worked out: never a literal's own temporary or a call's hidden one, so `pair = .[pair[1], pair[0] + pair[1]];` in a loop reads the old view whole first); `int.[1, 2, 3]` is a `[3]int` and `.[1, 2]` takes its type from where it's used. `.count` and `.data`, `a[i]`, `for a` (each element, `it` a copy) and `for * a` (`it` a pointer to each); an array's `.data` and `for *` need an array with an address, as `*a` does, so a parameter's elements stay read-only. Indexing a pointer is C's, unchecked. Growable arrays (`[..]T`) come with the `Basic` module (milestone 4), since they need the context's allocator (`growable arrays ([..]T) come with the Basic module, in milestone 4`, at the `[`). The rulings and their messages:
    - `[N]T`: N an integer known while compiling, from 0 up (`an array's count must be an integer, not 'float32'`, `an array's count must be known while compiling`, `an array's count can't be negative (-1)`, at N); `T` any type but `void`. No type is over 2^40 bytes: `'[1099511627777]u8' is too big`, at the `[`, and `'Huge' is too big` for a struct, at its name. A struct holding an array of itself holds itself; a view of itself, or an array of pointers to itself, is fine.
    - `a[i]`: `i` any integer, an untyped one an `int` (`an index must be an integer, not 'bool'`, at i); on anything but an array, a view, a string or a pointer, `'[]' needs an array, a view, a string or a pointer, not 'int'`, and on a `*void`, `can't index a '*void'; cast it to a pointer to something first`, both at the `[`. A constant index outside an array is `index 3 is out of bounds for '[3]int'`, at the index. An element is a place when its array is, and always a view's or a pointer's.
    - An array's `.count` is an untyped integer constant, as `size_of` is, so the array isn't evaluated for it; its `.data` is the address of its first element. Neither can be assigned to (`can't assign to an array's 'count'`); `.data` of an array without an address is `*a`'s message (`can't take the address of 'a': it's a parameter`). A view's two are its fields. Nothing else: `'[3]int' has no field 'size'`. Neither is reached through a pointer (`p.*.count`): on a pointer to an array, a view or a string, `'.count' isn't reached through a pointer, '*string'; write .*.count`.
    - `[N]T` converts to `[]T` wherever a value converts (a declaration, an assignment, an argument, a return, a cast), and to nothing else; nothing converts to an array but its own type. `.[a, b]` meeting an array must give its count (`'[3]int' has 3 elements, but this literal gives 2`), meeting a view becomes an array of its own count; meeting anything else, `a '.[' literal needs an array or a view type, not 'int'`; meeting nothing, `this literal's type isn't known; write it before the '.', as in int.[1, 2]`. A global array is a literal of constants; a global view's value is an array literal, which becomes a global array of its own (a relocation in the view's bytes points at it).
    - `for a` takes a's data and count once, before the first iteration, and goes up to the count (compared signed, so a view whose count was set below 0 runs no iteration). `for` over anything else: `'for' needs a range, an array, a view or a string, not 'int'`; `for *` over a range: `'for *' needs an array, a view or a string, not a range`.
    - A foreign procedure takes no array or view: `a foreign procedure can't take a '[3]int'; pass its .data`.
  - **Bounds checks**: an array's, a view's or a string's index is compared with its count, as an unsigned number after widening by its own sign, and a failure stops with `runtime error: index I is out of bounds (count C)`, at the `[`, I written by the index type's sign and C as signed; a view whose count was set below 0 has no index inside it. A constant index of an array is checked while compiling. `#no_abc` on a procedure (Jai's directive, after its results, before its body) or `rig build --no-bounds-checks` turns them off (`rig check` takes no such flag: it lowers nothing); nothing else does, and null checks stay, as does the compile-time error. A failing check calls `__rig_bounds_failed`, a procedure lowering adds to a module that needs it, which writes the message into a buffer of its own (the longest `PATH:L:C: runtime error: ` the module passes it, plus 73 bytes: 33 of fixed text and up to 20 for each number) and panics with it.
  - **Order**: an assignment works out where it writes (the target's operands left to right, then its checks) before the value; a compound one does so once. Several targets keep 2a's order: the call, then the targets. Indexing, anywhere, reads what it indexes (an array's address, a view's count and data, a pointer's value) before working out the index, and the element after, so `v[f()]` indexes `v` as it was before `f` ran, whatever `f` assigns to it.
  - **Strings**: a string literal is a `string` (its count the bytes without the zero C would need after them, which is still there, so a literal also converts to `*u8`); another `string` doesn't convert to `*u8`. `s[i]` is a `u8`. `==` and `!=` compare the bytes. A `[]u8` and a `string` cast to each other. A literal's bytes are read-only memory. Converting a string to a C string needs an allocation, so its helper comes with `Basic` too. The rulings and their messages:
    - `string` is `{ count: int; data: *u8; }`, a view of bytes laid out as `[]u8`, but a type of its own: `.count` and `.data` (places when the string is one), `s[i]` (always a place, bounds-checked as a view's element), `for s` (`it` a `u8`) and `for * s` (`it` a `*u8`) are a view's. A variable holds one (`x := "hi";`, its count 2).
    - Only a literal converts to `*u8`: `a value of type 'string' doesn't convert to '*u8' implicitly; its .data may not end with a zero` (an argument's message ends the same way, and so does a cast's, `can't cast 'string' to '*u8'; its .data may not end with a zero`). Writing a literal's bytes (`s := "abc"; s[0] = 65;`) is a memory error, the programmer's responsibility (6.4); nothing catches it yet.
    - `==` and `!=` take two strings, equal when their counts are and then each byte is; a string meets no other type (`mismatched types 'string' and '*u8' for '=='`), and has no order or arithmetic (`'<' needs numbers, not 'string'`, `'+' needs numbers, not 'string'`). Lowering compares them with `__rig_string_equal(count_a, data_a, count_b, data_b)`, an IR procedure it adds to a module that needs it, as it adds `__rig_bounds_failed`: the counts, then the bytes one at a time in a loop, no C call (so every backend has it); a count set below 0 has no bytes, as `for` sees it. The left operand's count and data are read before the right operand is worked out.
    - `cast(string) v` of a `[]u8` and `cast([]u8) s` of a `string` are the same view, retyped; nothing else converts or casts to or from `string` (`can't cast '[2]u8' to 'string'`).
    - A global may hold a literal as a `string`, a `*u8` or a `[]u8` (`greeting := "hi";`, `g : *u8 = "hi";`), in a struct's field or an array's element too: its bytes hold the literal's address through a relocation, as a global view's do its array's. A string that isn't a literal isn't known while compiling, nor is a literal's address cast to an integer.
    - A foreign procedure takes no string: `a foreign procedure can't take a 'string'; pass its .data, which may not end with a zero, or a literal`, and returns none (`a foreign procedure can't return a 'string' yet`).
  - **Foreign procedures** take and return numbers, bools and pointers only, for now: a struct, array, view or string is passed to C through a pointer (`.data`). Passing C structs by value follows each platform's C rules, which come with milestone 6's bindings.
  - **How it's compiled**: an aggregate is bytes in memory, copied with `memmove` semantics (two values may overlap), never a value in a register; a procedure's aggregate parameter is a pointer to a copy the caller makes, and an aggregate result goes through a hidden pointer the caller passes. The IR knows nothing of structs, so every backend gets them free. In detail: the hidden pointers come first, one per aggregate result in result order, then the visible parameters, and the IR's results are the scalar ones only; `return` copies each aggregate value into its hidden pointer. The caller passes a fresh temporary of its own as each hidden pointer, never the place the result is going, and copies the temporaries there after the call; it copies each aggregate argument into a temporary as soon as it's worked out, and the callee never writes it. A literal is built in a temporary, zeroed first (padding included), then copied. A global struct is bytes in the program's file, its literal's or zeros.

### 6.6 Memory and the context
- Manual memory: allocate and free, arenas. No smart pointers, no GC, no borrow checker.
- **The implicit context**: every call between Rig procedures passes a hidden context pointer. It holds the current allocator, temporary storage, a logger, the assertion handler, the thread index and a user-data slot. `push_context` / `push_allocator` change it for a block. C functions don't receive it; C-callable Rig procedures set one up. (Contents: Claude's call, from Jai)
- **Temporary storage**: a built-in arena, reset all at once (per frame, per request).
- `defer`.
- **The memory debugger** in debug builds (how "the language tells the programmer"): every allocation recorded with a stack trace; leaks reported at exit; double frees reported with both stack traces; freed memory poisoned; optionally freed pages made inaccessible so a use-after-free crashes at the bad line. Off in release builds.

### 6.7 Errors
- Plain **multiple return values**; nothing special for errors. No exceptions. Written (Claude's call, as Jai shows it) `divmod :: (a: int, b: int) -> int, int { return a / b, a % b; }`, received by `q, r := divmod(7, 2);` or `q, r = divmod(7, 2);`; a call used as one value gives its first result.
- Milestone 2a's details (Claude's calls): a `return` gives exactly one value per result (`'divmod' returns 2 values, but this return gives 1`), each converting to its result's type, and every path must return. Names or targets receive exactly as many as the call returns (`'divmod' returns 2 values, but 3 names receive them`), from a call only (`only a call can give several values, as in q, r := divmod(7, 2);`): each name gets its result's type, and each result converts to its target's type as an assigned value would. Several targets take only `=`. `return divmod(a, b);` is one value, the call's first result, not two. A foreign procedure returns at most one value, as C does (`a foreign procedure can return at most one value`). Several results are returned as one struct of them, which only Rig's own procedures agree on.
- Ignoring a returned value is allowed. Any warning about it can be switched off; warnings never block a build unless asked to.

### 6.8 Generics
- Polymorphic procedures and structs with `$T`, one compiled copy per type, no declared constraints; `#modify` to check or adjust types at compile time.

### 6.9 Compile-time execution and metaprogramming
- `#run expr` runs any code at compile time and bakes the result in.
- **The build file is a program**: `rig build` runs `build.rig`, which sets compiler options and adds files. No other build system.
- `#insert` inserts generated code.
- Type information at run time (`type_info`, `Any`), which `print` uses.
- Later: metaprogram hooks that receive each declaration as it is checked.
- Compile-time code may do anything Jai's may (including network access); "builds are offline" is a rule of Rig's own toolchain, not a restriction on compile-time code. (Claude's call)
- **Compile-time code calls C from the start (milestone 3).** The standard library is built on C functions (section 4), so even `print` in a `#run` needs foreign calls. The IR interpreter's memory is real native memory with the target's exact layouts, and it calls foreign functions through **hand-written call thunks** for the Windows x64 and System V conventions (no libffi, no JIT). (Claude's call)
- **What `#run` results can be baked into the program:** plain data, meaning integers, floats, booleans, strings, arrays, views and structs of them. Pointers inside them are allowed only into data that is baked too, and are relocated; any other pointer is a compile error. (Claude's call)
- Order: `#run` and the build file first, then `#insert` and type info, then the hooks. (Claude's call)

### 6.10 Enums, unions and tagged unions
- `enum` (with a chosen integer size), `enum_flags`, untagged C-style `union`, `if x == { case ...; }`.
- **Plus tagged unions** (Nuno, going beyond Jai): a union that knows which member it holds, and a switch over it that must handle every case, so reading the wrong member or forgetting a case is a compile error.
  - **A member is read only inside a switch case that binds it** (as Odin's type switch); `x.member` on a tagged union is not allowed. No flow analysis in the checker. (Claude's call)
  - **The switch must name every member, or have an explicit `else`.** `else` is the programmer's choice to opt out, at the cost of not being told about members added later. (Claude's call; Jai has the same idea for enums, `if #complete x == { ... }`, which Rig also takes.)
  - **Layout:** the tag (the smallest integer that fits, or a chosen one), then the members overlapping, as a C struct holding an enum and a union, documented so C can read it. (Claude's call)

### 6.11 Operators, threads
- Operator overloading for structs (existing operators only, never for built-in types), `#symmetric`.
- Threads in the library (`Thread` module, mutexes, atomics); each thread has its own context and temporary storage; nothing in the syntax (no async/await, no goroutines).

### 6.12 Standard library
- Grows like Jai's (Nuno): basics first, then breadth toward Jai's set (windows, input, drawing, sound, UI), largely through modules wrapping C libraries.
- Version 1 (Claude's call): `Basic` (print, memory, arrays), `String`, `File`, `Math`, `Hash_Table`, `Sort`, `Thread`, `Process`, plus the memory debugger. Every module readable, fast, written in Rig.

## 8. Dependencies

- **Go's way, no central registry** (Nuno): a dependency is named by its URL and pinned to a version (a git tag such as `v1.2.0`); a **lock file** records each dependency's checksum.
- **Which hosts:** those that serve a tagged version as an archive over HTTPS: GitHub (`https://github.com/OWNER/REPO/archive/refs/tags/TAG.tar.gz`, which redirects to `codeload.github.com`), GitLab (`https://gitlab.com/GROUP/PROJECT/-/archive/TAG/PROJECT-TAG.tar.gz`) and Gitea/Forgejo (`https://HOST/OWNER/REPO/archive/TAG.tar.gz`; Codeberg and gitea.com are known, any other Gitea or Forgejo host has to be declared as one). A plain git server that speaks only the git protocol isn't supported; `rig` never implements git itself. (Claude's call)
- **The checksum is of the extracted file tree** (file paths and contents, in a defined order, with the archive's top-level directory removed, since hosts name it differently), not of the archive: hosts don't keep archives byte-identical (GitHub's changed for a day in January 2023 and broke pinned builds), and Go hashes file trees the same way. (Claude's call)
- **Builds are offline** (Nuno): building reads only the code and the local cache, verifies every dependency against the lock file, and fails with a clear message if something is missing. **Fetching is an explicit command** (`rig get URL@VERSION`, `rig fetch`), the only code that opens a network connection. Vendoring (copying dependencies into the repo) is a one-command option. (Details: Claude's call)
- Fetching downloads archives over HTTPS rather than running `git`: on Windows through WinHTTP, part of Windows, which uses the OS's TLS and certificate store; on Linux through **mbedTLS** (Apache-2.0, fine in an MIT project with its licence text included), linked into the compiler and reading the system's CA certificates (`/etc/ssl/certs`). BearSSL was considered and rejected: beta quality, no TLS 1.3, no recent releases. The network code is a separate module the compiler core never calls. (Claude's call)
